# M07：沿流式工具调用阅读代码

本阶段按既有偏好不布置动手题。实现与测试通过不代表已经独立掌握。

## 建议阅读顺序

1. `contracts/stream.py`：片段、最终用量和关联事件分别保存什么，以及为何拒绝跨类型载荷。
2. `providers/stream.py::collect_reply`：index 如何隔离调用，何时才生成完整 Message。
3. `runtime/loop.py::Runner._loop`：增量观察与工具执行如何衔接，哪里检查 ID 和预算。
4. `providers/deepseek.py::DeepSeekProvider.stream`：SDK 字段如何转换为内部类型。
5. `observability/trace.py::EventRecorder`：内存正文与默认落盘元数据的区别。
6. `tests/test_streaming.py`：非法第二个调用为何让第一个也不写；审批中取消为何没有 ToolStarted。

## 一次执行轨迹

```text
第一回合开始
收到调用 a 的路径片段
收到调用 b 的路径片段
收到调用 b 的内容片段
收到调用 a 的内容片段
收到结束标记，流正常结束
组装并校验 a、b，产生两个 ToolCallReady
询问 a 的权限 → 同意 → 校验工具参数 → 开始写入 → 返回结果
询问 b 的权限 → 同意 → 校验工具参数 → 开始写入 → 返回结果
回合完成
第二回合携带两个结果请求模型
收到文本片段，组装最终回复
回合完成，运行完成，写摘要
```

如果在结束标记前断流：已收到的参数仍只是候选数据，没有实际工具调用。
如果在审批时取消：不进入注册表实际执行分支，同批后续调用不会开始。
即使模型已生成合法 JSON，依然需要等回复完成，避免后续片段破坏已执行调用的含义。

## 三个取舍

- 先保留完整回复边界，再执行工具：更容易证明不完整参数不会产生副作用，但不提前执行已完成的单个调用。
- 默认只保存元数据：减小敏感内容落盘风险，但不能单靠 Trace 还原输入；回放依赖显式受控脚本。
- 使用上下文变量传递关联记录器：原有 executor 接口不变；新执行器需要遵循相同事件约定，才能记录内部阶段。

## 本地运行

离线演示，不使用密钥：

```bash
uv run --locked python -m codepilot.m07_demo
```

真实演示只在明确授权和配置环境变量后运行：

```bash
uv run --locked --env-file .env python -m codepilot.m07_demo --live
```

每次启动 live 都会新建三次请求额度；不要把重新运行当作没有额外费用的离线测试。
本轮已经完成真实验证，不需要为了读代码再次调用。

真实轨迹是两次模型请求：第一次请求读取临时 number.txt，工具读到 17，第二次模型输出 17。
输入 Token 是供应商累计 834，输出 39；费用暂未计算，null 不代表零。
后续 M08 再处理受限并发、资源串行与排队取消，本轮工具仍按顺序执行。
