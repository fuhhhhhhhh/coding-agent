## 一次执行轨迹

运行 `uv run --locked python -m codepilot.demo codepilot.example.toml`。

1. main 读取 TOML，Config 验证只允许 fake/fake-m01。
2. FakeProvider 初始化两个 assistant 响应，深拷贝脚本到独立 deque。
3. collect_demo_events 构造第一条 user Message，complete 校验非空请求，pop 文本；2 → 1。
4. 构造另一个独立 user 请求，complete pop 带 call-1 的工具请求；1 → 0。
5. 演示入口给两个回复分配相同 session/run、不同 turn，以及序号 1/2。
6. main 将两个 AgentEvent 序列化打印；程序退出。没有执行 read_file。

轨迹可对照 `docs/evidence/M01-demo.jsonl`。
若第三次请求，complete 在 pop 前抛 FakeProviderExhausted；没有新的回复。
可运行 `uv run --locked pytest -q tests/test_fake.py -k exhaustion` 观察故障验证。

## 三道理解题

1. 若 user 消息带 tool_calls，代码在哪里拒绝？若 tool_result.call_id 对不上历史中的调用，
   当前能否拒绝？为什么两种检查需要的数据不同？
2. 为什么 Provider.complete 只接收和返回内部 Message？将某个供应商 SDK 响应直接返回，
   会迫使哪些调用方或测试跟着变化？结合本项目入口回答。
3. FakeProvider 的脚本长度从 2 到 0，与 RunState 从 running 到 completed 有什么区别？
   当前是谁分配 session/run/turn ID，未来会话、回合、工具执行状态各应由谁管理？
