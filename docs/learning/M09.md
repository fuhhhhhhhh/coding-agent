# M09 学习记录：执行后端、容器生命周期与独立验证

## 推荐阅读顺序

你已有 CoreCoder 和前八阶段基础，不需要逐文件通读。按一条正常链路、一条取消链路、一条验证链路读即可：

1. `src/codepilot/workspace/base.py`：先看 `ExecutionBackend` 和 `find_backend`，记住 Runtime 依赖的是行为契约，生命周期管理能穿过权限与调度包装器。
2. `src/codepilot/workspace/models.py`：看资源限制、命令结果和审计事件分别表达什么。
3. `src/codepilot/workspace/local.py`：读 `start -> execute/run_argv -> cancel -> close`，这是最容易单步理解的参考实现。
4. `src/codepilot/workspace/docker.py`：重点读 `start`、`_create_command`、`execute`、`cancel`、`cleanup_stale` 和 `_verify_worker`。
5. `src/codepilot/workspace/worker.py`：确认容器没有另一套工具逻辑，它仍调用现有 `ToolRegistry`。
6. `src/codepilot/evals/verifier.py`：读 `IsolatedVerifier.verify` 和 `_apply_candidate`，理解候选与验收材料如何隔离。
7. `src/codepilot/evals/harness.py`：只看 `run` 中后端的创建、跨尝试复用和 finally 清理，以及开发测试如何走同一后端。
8. 最后读 `tests/test_workspace_backends.py`、`tests/test_workspace_docker_live.py` 与 `tests/test_isolated_verifier.py`，区分控制器契约断言、真实内核行为和验证材料隔离。

`common.py` 是容量和文件边界细节，`__init__.py` 只是公开接口，第一遍可以跳过。Dockerfile 与锁定依赖应在理解控制器命令后再读。

## 整体流程

控制器继续持有模型、权限和调度。工具调用通过权限后进入调度器，再进入 ExecutionBackend。Local 后端直接调用现有注册表；Docker 后端把同一个 `ToolCall` JSON 发给容器 worker。worker 在 `/workspace` 建立现有六工具注册表，所以 read、write、edit、glob、search、shell 与开发测试看到同一文件状态。

Docker 后端的生命周期属于整个 task/trial，不属于单个工具。这样连续编辑不会丢失状态，取消也能以容器为边界停止全部执行。Harness 在多次纠错尝试间复用这个后端，结束时由 `finally` 清理。

独立验证不复用 Agent 容器。它从同一可信初始源创建新工作区，只应用候选文件差异，再注入 Agent 未见的验证材料并启动新的后端。评分读取的是重新构造的候选，不信任 Agent 工作区中的测试结果。

## 一次可观察轨迹

```text
backend_started(container_id=... outcome=ready)
tool_executed(call_id=edit-1 outcome=success)
command_executed(outcome=exit_0)
resource_sampled(cpu_percent=... memory_bytes=...)
artifact_exported(outcome=success)
backend_closed(outcome=removed)
```

轨迹不包含编辑内容、路径、命令或环境值。Runtime 原有 Trace 负责模型回合、审批与调度；Backend Journal 负责系统执行环境。两者用不同记录避免把高敏感参数为了“方便调试”默认落盘。

## 与 Claude Code 风格对齐的部分

这里参考的是公开可观察的交互与安全原则：操作在明确工作区内发生，敏感能力经过权限判断，执行环境采用默认收紧策略，用户能看到工具与生命周期结果。代码没有假装复制 Claude Code 的内部实现。

本阶段最重要的风格变化是把三件事分开：权限回答“允许做吗”，调度回答“何时能做”，执行后端回答“在哪里做、如何停止和清理”。容器不能替代审批，审批也不能阻止一个已获准 Shell 访问宿主系统；两者需要同时存在。

## 理解题与答案

### 1. 为什么 ExecutionBackend 不能只包装 `shell`？

因为 Coding Agent 的状态变化还来自 `write_file`、`edit_file`、搜索和验证命令。只把 Shell 放进容器，会出现文件工具改宿主目录、测试却读容器目录的双工作区，也会让取消和审计只覆盖部分副作用。统一后端让所有执行共享任务生命周期和工作区。

### 2. 为什么取消 `docker exec` 后还要 `docker kill`？

`docker exec` 的 CLI 是控制器本地进程，容器内命令是另一个执行实体。CLI 被取消或管道关闭，不足以证明容器内进程树停止。当前实现选择杀死整个任务容器，牺牲取消后的复用，换取明确的停止边界；后续调用也被拒绝。

### 3. 为什么独立验证要从初始源重建，不能直接在 Agent 工作区放一个隐藏测试？

Agent 对自己的工作区有写权限，文件名隐藏并不等于不可修改。直接验证该目录会让删除测试、伪造配置或预建同名文件影响评分。从可信源重建候选，再在候选应用后注入保留目录，才能把“候选代码”和“评分材料”的所有权分开。Docker 再负责限制验证代码执行时的系统访问。

## 当前真实边界

Local 后端已用真实进程验证同工作区、超时、取消、产物和审计。Docker 控制器用 fake transport 验证命令协议与故障分支，并在当前 Linux Rootless Docker 上真实验证同工作区、断网、凭据不转发、只读根层、零 capability、`NoNewPrivs`、CPU/内存限制、取消与遗留清理。

真实验收暴露了三个 fake 无法证明的问题。第一，Docker 29 的 `--mount` 不接受独立 `rw` 字段，bind 默认已可写。第二，rootless 容器中的 UID 1016 会映射为 subordinate UID，无法写宿主用户目录；namespace 内 root 才映射为宿主普通用户。第三，exec 子进程被 OOM 杀死时常驻容器仍运行，容器级 `OOMKilled` 为 false，必须观察 cgroup 的命令前后增量。这也是为什么真实集成测试必须与命令构造单元测试并存。

边界仍然存在：Docker 与宿主共享内核，bind 工作区没有硬磁盘配额，rootful daemon、Windows 和 macOS 未验证。用户级 Rootless Docker 降低了 daemon 权限范围，但不能把它描述成 MicroVM 或绝对安全环境。
