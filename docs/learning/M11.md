# M11 / P2 学习记录：直接 Git 工作流与可选隔离

## 推荐阅读顺序

1. `src/codepilot/app/service.py` 的 `CodePilotApplication.run` 与 `_create_backend`：先看默认目录如何直接进入后端，以及显式隔离分支在哪里发生。
2. `src/codepilot/tools/shell.py` 的 `ShellTool.run`：看所有 Git 写操作如何复用进程权限、超时与取消。
3. `src/codepilot/config.py` 的 `GitWorkspaceConfig`：看隔离为何是可选配置。
4. `src/codepilot/workspace/git.py` 的 `GitTaskWorkspace.prepare`、`finish`、`cleanup`：这是隔离交付状态机。
5. `src/codepilot/app/service.py` 的 `CodePilotApplication.run`：看任务工作树如何进入既有 Provider、权限、
   Context、调度和后端链，以及异常时为什么仍调用交付逻辑。
6. `src/codepilot/tools/git_status.py` 与 `git_diff.py`：看只读观察捷径。
7. `tests/test_git_workspace.py`：从原生 Git 工作流、并行隔离和重放失败反查契约。

## 一次执行轨迹

```text
codepilot 输入任务
  -> 生成 session/task/run ID
  -> 默认把当前目录直接交给 Local/Docker 后端
  -> Agent 用文件工具修改，用 shell 执行原生 Git 和测试命令
  -> 修改立即留在当前目录

codepilot --worktree 输入隔离任务
  -> 解析 base commit
  -> git worktree add --detach
  -> 后端只绑定任务 worktree
  -> Agent 用文件、Shell、git_status/git_diff 完成任务
  -> Provider、容器和 Context 临时资源先关闭
  -> 收集全部 Git 修改并导出二进制 patch
  -> 从同一 commit 创建 replay worktree
  -> git apply --check -> git apply
  -> 可选固定验证 argv
  -> 删除 replay worktree
  -> 无修改则删除任务 worktree
  -> 有修改则保留任务 worktree、patch 和 0600 ownership manifest
  -> CLI 展示交付位置与复验状态
```

这里有三个不同结论：Runner `completed` 只表示模型循环正常结束；`replay_status=passed` 表示补丁能在
固定起点应用；`verification.passed` 才表示项目配置的独立判据通过。CLI 只有在 Runtime 和交付都没有
失败时才返回零。

## 理解题与答案

### 1. 为什么默认直接工作区不要求 Git 仓库干净？

交互式 Agent 的主要对象就是用户当前正在编辑的目录。脏状态可能是任务输入的一部分，强制干净会排除
真实开发流程，并把结果留在另一个目录要求用户手动搬运。产品因此直接保留并修改当前状态。

### 2. 为什么补丁重放要创建第二个 worktree，不能只在 Agent 工作树运行测试？

Agent 工作树可能包含补丁没有捕获的文件、模式或 index 状态。在同一目录测试通过不能证明交付物完整。
从相同 commit 建立 replay worktree 并只应用导出的 patch，才能验证接收方实际拿到的内容。

### 3. 为什么 commit、branch、fetch、pull、push 不各自实现一个工具？

Git 已经提供完整 CLI、配置、认证和错误语义。逐个包装会形成第二套不完整 Git API，并持续遗漏参数。
Shell 已有 `process` 权限、调度、超时、取消和输出契约，所以写操作直接复用它；只读 status/diff 单独
存在，是为了让观察无需批准 Shell。Docker 默认断网，远端操作目前只能在 Local 后端实际联网；显式
worktree 的 Git 元数据也不挂入容器，因此该组合目前只支持控制器侧 status/diff。

## 当前边界

显式 worktree 模式导出并验证补丁，但不自动应用到源工作树，也没有处理多个任务补丁的自动合并。默认
直写模式无需应用补丁。worktree 只隔离
Git 文件修改，不隔离端口、数据库、网络服务和用户缓存；这些仍由 Docker 与权限策略负责。交互会话
仍不共享上一条任务的模型历史，持久会话和保守恢复属于后续阶段。
