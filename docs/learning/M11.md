# M11 / P2 学习记录：从用户仓库到可重放补丁

## 推荐阅读顺序

1. `src/codepilot/config.py` 的 `GitWorkspaceConfig`：先看哪些安全与验证选择由产品配置固定。
2. `src/codepilot/workspace/git.py` 的 `GitTaskWorkspace.prepare`、`finish`、`cleanup`：这是本阶段主状态机。
3. `src/codepilot/app/service.py` 的 `CodePilotApplication.run`：看任务工作树如何进入既有 Provider、权限、
   Context、调度和后端链，以及异常时为什么仍调用交付逻辑。
4. `src/codepilot/tools/git_status.py` 与 `git_diff.py`：看模型如何只读观察自己的修改。
5. `src/codepilot/workspace/docker.py` 的 `execute` 和 `_verify_worker`：理解两个 Git 工具为何在控制器侧执行。
6. `tests/test_git_workspace.py`：从并行隔离、完整补丁、重放失败和保守清理反查契约。

## 一次执行轨迹

```text
codepilot 输入任务
  -> 生成 session/task/run ID
  -> 检查源仓库干净并解析 base commit
  -> git worktree add --detach
  -> 后端只绑定任务 worktree
  -> Agent 用文件、Shell、git_status/git_diff 完成任务
  -> Provider、容器和 Context 临时资源先关闭
  -> 收集全部 Git 修改并导出二进制 patch
  -> 从同一 commit 创建 replay worktree
  -> git apply --check -> git apply
  -> 可选固定验证 argv
  -> 删除 replay worktree
  -> 无修改则删除任务 worktree
  -> 有修改则保留任务 worktree、patch 和 0600 ownership manifest
  -> CLI 展示交付位置与复验状态
```

这里有三个不同结论：Runner `completed` 只表示模型循环正常结束；`replay_status=passed` 表示补丁能在
固定起点应用；`verification.passed` 才表示项目配置的独立判据通过。CLI 只有在 Runtime 和交付都没有
失败时才返回零。

## 理解题与答案

### 1. 为什么默认拒绝带未提交修改的源工作树，而不是直接从 `HEAD` 建 worktree？

因为用户当前看到的代码与 `HEAD` 可能不同。新任务只看到 commit 内容时，模型会基于错误起点修改，
最后补丁也无法表达源目录中原有的未提交约束。拒绝能在任何后端或模型副作用前暴露这项差异。

### 2. 为什么补丁重放要创建第二个 worktree，不能只在 Agent 工作树运行测试？

Agent 工作树可能包含补丁没有捕获的文件、模式或 index 状态。在同一目录测试通过不能证明交付物完整。
从相同 commit 建立 replay worktree 并只应用导出的 patch，才能验证接收方实际拿到的内容。

### 3. 为什么 Docker 中的 `git_status` 和 `git_diff` 在控制器执行？

Git worktree 根目录中的 `.git` 是指向源仓库管理区的指针，而 Docker 只允许挂载任务文件，不能为了
两个只读查询暴露整个源仓库 Git 元数据。控制器工具只执行固定只读 argv，并继续经过权限、调度和
Trace；文件编辑和 Shell 仍由容器隔离。

## 当前边界

本阶段导出并验证补丁，但不自动应用到源工作树，也没有处理多个任务补丁的自动合并。worktree 只隔离
Git 文件修改，不隔离端口、数据库、网络服务和用户缓存；这些仍由 Docker 与权限策略负责。交互会话
仍不共享上一条任务的模型历史，持久会话和保守恢复属于后续阶段。
