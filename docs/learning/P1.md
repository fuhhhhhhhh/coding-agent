# P1 学习记录：从 CLI 到一次完整 Agent 运行

## 推荐阅读顺序

你已经读过 CoreCoder 和 M01—M10，不需要逐文件阅读。按一次 `codepilot run` 的调用方向读：

1. `src/codepilot/ui/cli.py`：看 `main`、`_interactive`、`_run`，理解交互与单次命令如何汇入同一执行函数。
2. `src/codepilot/config.py`：看 `load_product_config`、`_select_optional_config` 与 `_read_product_config`，理解 YAML/TOML 层级和为什么配置里只有密钥变量名。
3. `src/codepilot/app/models.py`：先记住 `RunIdentity`、`ResourceOwnership` 和 `ProductRunResult` 三个产品契约。
4. `src/codepilot/app/service.py`：重点读 `CodePilotApplication.run`，沿 backend → scheduler → permission → context → provider → runner 追踪装配和反向清理。
5. `src/codepilot/ui/renderer.py`：确认 UI 只消费事件，没有第二套 Agent 循环。
6. `src/codepilot/providers/openai_compatible.py`：读 `stream` 和 `messages_to_openai`，特别关注空占位分片为什么在协议边界丢弃。
7. `tests/test_product_app.py`：依次读正常链、Provider 初始化失败、后端启动失败和取消测试。
8. `tests/test_cli.py` 与 `tests/test_deepseek.py::test_compatible_gateway_ignores_empty_tool_placeholders`：核对正式命令输出与真实故障的确定性回归。

第一次阅读可以跳过各包 `__init__.py` 和旧 demo。要理解 Docker 细节时再回到 `workspace/docker.py`；P1 没有重写后端。

## 一次完整执行轨迹

```text
codepilot
  -> 自动读取用户级或项目 .codepilot/config.yaml
  -> _interactive 读取一条任务
  -> argparse 得到显式 CLI 覆盖
  -> load_product_config 依次合并用户、项目、显式文件、CLI
  -> CLI 生成 session/task/run ID 并展示 product_started
  -> CodePilotApplication 校验工作区、状态目录和密钥环境
  -> 构造 Local 或 Docker backend
  -> 包装 ContextManager
  -> 包装 ScheduledExecutor
  -> 包装 PermissionedExecutor
  -> 用 Permission 的最终工具 Schema 构造 Provider
  -> backend.start
  -> Runner 请求模型、执行工具、回传 ToolResult、得到最终回答
  -> EventRecorder 落脱敏 Trace，并把事件副本交给 EventRenderer
  -> Provider.close -> backend.close -> ArtifactStore.cleanup
  -> 返回 ProductRunResult，CLI 展示结果并选择退出码
  -> 回到 codepilot>，等待下一条独立任务
```

这条轨迹中，Runtime 仍然不知道终端参数和输出样式；UI 也不知道 SDK 和工具如何执行。composition root 是唯一知道所有具体实现的地方。

`codepilot run "检查工作区"` 会跳过交互循环，从 `_run` 开始执行，适合脚本、CI 和固定验收。
两种入口不会形成两套 Agent 行为。当前 `_interactive` 复用 session ID 只用于关联本次进程中的多条任务；
每条任务仍重新建立 Provider、Runner 和规范历史，因此暂时不是可连续追问的持久对话。

## 这次工作解决了什么

此前各个 `mXX_demo.py` 分别证明组件机制，用户没有一个稳定入口把 Provider、权限、调度、Context 和 Docker 放在同一次运行中。P1 增加的核心价值是明确组合关系和资源所有权：同一个 run ID 同时出现在 Runtime Trace、工具事件和产品结果中，异常退出也由同一个生命周期关闭。

P1 还把真实模型配置带入正式入口。`openai-compatible` 是协议边界，不是某个中转站专用类；网关地址、模型和密钥环境变量均来自配置。真实 Qwen 测试发现并修复了 mock 未覆盖的空 tool-call 占位分片，这正是持续真实冒烟的价值。

补充的真实写入实验还展示了“工具错误是下一轮模型输入”的作用。模型第一次 edit 没有满足精确匹配，工具没有猜测写入；模型读取实际文件后修正参数。Shell 调用随后停在权限层，直到终端明确批准才进入 Docker。这个过程同时验证了编辑冲突保护、错误反馈、自我修正、审批和容器执行，证明的范围比只读 glob 更完整。

## 理解题与答案

### 1. 为什么 composition root 应该知道所有具体组件，而 Runner 不应该读取配置并自己创建它们？

Runner 的职责是维护模型—工具循环及唯一终态。如果它同时读取 TOML、创建 Docker、选择权限和渲染终端，核心循环将无法用 fake 独立测试，资源清理也会分散。`CodePilotApplication` 集中完成一次装配，Runner 继续只依赖 Provider、ToolExecutor、Context 和 Recorder 的内部边界。

### 2. 为什么 Provider 初始化失败也要调用 backend.close，即使后端还没有 start？

构造和初始化边界未来可能变化，某些后端也可能在启动前分配本地句柄。只要资源对象已经归本次 run 所有，就立即登记统一 close，调用方无需猜测失败发生到哪一步。close 必须幂等并能处理未启动状态，这让正常、部分启动和异常都走相同退出路径。

### 3. 为什么交互模式复用 `_run`，而不是长期持有一个 Runner？

当前 Runner 的历史、预算和终态都是一次运行所有权，结束后不能再次启动工具。强行复用会破坏唯一终态和
资源清理约束。交互外壳因此只复用 session ID，并为每条输入建立新的 task/run；P5 引入持久会话契约
后，才由会话层明确选择哪些历史进入下一次运行。

## 当前边界

这些 ID 目前只关联一次进程内运行，不能恢复；状态目录也没有 SQLite 索引。Local 后端仍是可信宿主执行，Rootless Docker 的已有基线不等于完整安全沙箱。P2 将给 task ID 绑定固定 Git commit 和 worktree，并实现可审查、可重放的补丁交付；P3 才继续加固输出、配额、秘密和 Action 权限。
