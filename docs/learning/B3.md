## 用一段话理解改动

这次让 CodePilot 更适合连续工作：退出后重开可以沿用上次压缩的历史，下次只补进新发生的事情；主模型、摘要和重试都从同一个持久预算里扣次数与 Token，不会重开就清零。网络失败只有明确没有被接受的情况才有限重试，半截工具调用绝不会继续执行。另接入 Responses 协议，并用两个真实仓库验证了“先测试失败、修改、重测通过、重开后接着讨论”的完整过程。你也可以输入 `/compact` 主动压缩，它不会顺手改文件。

## 一次实际轨迹

真实 Chat Completions 修复：6 次请求、6 次工具；Responses 修复：7 次请求、9 次工具。两者公开及隐藏验收通过。各自新进程续问一次请求；触发压缩的进程各两次请求（摘要+主回复），再开进程各一次请求复用检查点；主动 compact 各一次摘要、零工具。完整 usage、工具成功/失败和独立核对在 JSON，Runtime completed 不能替代独立判定。

## 三道理解题及答案

**1. 为什么出现 500 或读取超时不能直接重试？**

服务器可能已接受请求，客户端只是没有拿到结果；重发会重复付费或产生另一次不兼容工具计划。只有 429 明确拒绝或可证明未发 HTTP 的建连错误进入有限退避，已消费的流不重放。

**2. 检查点为什么既有 covered_messages 又有 source_digest？摘要为什么不能用 system 角色？**

覆盖数定位被压缩前缀，哈希确认它仍对应规范历史，完整回合边界保护工具调用与结果配对。摘要来自模型及工具数据，不能因为经过压缩就变成高权限授权。摘要中的测试结论仍需独立证据，不能当成控制器事实。

**3. resume、主请求和摘要怎样避免重置预算？**

所有网络尝试在同一 SessionStore 中先持久预留，以 attempt_id 关联 usage；新进程读取 request_attempts 与 pending。无 usage 或崩溃的请求继续占额度，即使用户协调旧 run 也不伪造零成本。无工具摘要器共享同一 RequestBudget，不另开免费额度。
