# M03：沿一次工具调用理解注册层

按用户要求不设置动手题。以下阅读顺序集中在工具契约、执行前校验和副作用边界。

## 必读入口

1. `tools/base.py::Tool` 与 `ToolSpec`：一份参数模型如何同时约束 Schema 和实际执行。
2. `tools/registry.py::ToolRegistry.execute`：查找、校验、超时及错误归一化。
3. `tools/workspace.py::Workspace.resolve`：路径如何从模型字符串变成受边界约束的绝对路径。
4. `tools/edit_file.py::EditFileTool.run`：为什么零匹配和多匹配都不能写。
5. `tools/shell.py::ShellTool.run`：输出排空、取消和当前进程回收。

每个工具类现在位于独立模块：`read_file.py`、`write_file.py`、`edit_file.py`、`glob.py`、
`search.py` 和 `shell.py`。`file_common.py`、`discovery_common.py` 只保存共享策略，
`factory.py` 是唯一集中组装入口；工具实现之间不互相导入。

## 正常轨迹

`docs/evidence/M03-happy.jsonl` 中 Fake Provider 依次请求六个工具：

1. read_file 读取故意错误的 calculator.py。
2. edit_file 唯一替换减法实现。
3. write_file 创建 result.txt。
4. glob 列出 Python 文件。
5. search 找到修复后的代码及行号。
6. shell 在临时工作区运行真实 unittest，返回 exit_code=0 和 OK。
7. Provider 返回无调用文本，Runner 以 completed 结束。

每次调用先经过 ToolRegistry。Pydantic 校验失败时不会进入 Tool.run，因此“错误参数无副作用”由结构保证，
而不依赖每个工具记得重复检查字段。

## 三个设计取舍

**Schema 只有一个来源。** ToolSpec 不保存手写参数 Schema，而是读取 arguments_model。若分别维护两份，
模型可能按旧 Schema 发出参数，而执行器按新规则拒绝，或未知字段悄悄进入副作用代码。

**路径边界独立于具体文件工具。** Workspace 集中拒绝绝对路径、父目录和符号链接。这样新增文件工具时
可以复用同一边界；但 Shell 可以访问操作系统，不能靠 Workspace 文件检查限制，权限与隔离仍需后续实现。

**错误结果与异常分层。** 模型可纠正的问题变为 ToolResult(is_error=True)；真正意外的实现异常由 Runner
统一转译。Shell 非零退出使用 ToolOutput，以便同时保留诊断正文和失败标记。

## 理解题

1. 为什么 ToolRegistry 必须在调用 `Tool.run` 之前使用 arguments_model 校验，而不能只把 JSON Schema 给模型？
2. `Workspace.resolve` 为什么既逐段拒绝符号链接，又在最后执行 `relative_to(root)` 边界检查？
3. Shell 超时为什么需要同时等待进程退出并处理 stdout/stderr 读取任务？当前实现仍缺少哪一层进程保证？
