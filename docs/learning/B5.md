# B5：怎么知道 Agent 真正做成了任务

这轮把“看起来做完”变成一条能独立核对的交付链。现在可以不花模型请求检查环境、查看变化和权限、
运行受控测试、预览并清理已登记资源；评测则真的从固定 commit 取代码，在临时仓库加入缺陷与已有改动，
让 CodePilot 正常修复，再用它没见过的测试检查。报告同时保留模型怎么说、工具做了什么、运行怎么结束，
以及独立测试怎么判。一次失败和一次成功都保存，不能只挑好看的结果。

## 推荐阅读顺序

1. `src/codepilot/ui/cli.py:build_parser/main` → `app/operations.py:test_command`：先看用户实际入口，
   理解维护与测试为何零模型请求，以及进程操作为什么仍经过审批。
2. `app/service.py:_execute/_execute_direct` 与 `contracts/run.py`：看统一执行装配如何支持用户单次命令，
   为什么使用 command_requested 而不是伪造 model_requested，Trace/事实/取消怎样复用。
3. `evals/product.py:ProductTask/Suite/ProductHarness.run`：抓住固定清单、总预算、输出目录所有权、
   镜像别名与隐藏材料冻结。持久结果不等于可以自动重放中断任务。
4. `ProductHarness.trial/verify`：沿 checkout → 精确注入 → 基线失败 → 正常应用 → 保护检查 →
   新环境隐藏测试走一遍；重点理解“修复后 Git diff 为空也可能是正确修复”。
5. `permissions/approval.py:ConsoleApproval.approve`、`ui/renderer.py:__call__`：看真实 PTY 输入取消、
   非 TTY 拒绝和审批期间缓冲为何能避免旧线程抢输入及提示交错。
6. `tests/test_b5*.py` → `docs/evidence/B5-*`：先看空修复/改测试/版本漂移/验证器失败的反例，
   再读首轮完整失败与第二轮的四层结果；最后看安装和仍被阻断的发布条件。

## 一次真实执行轨迹

用户 eval 提交可信清单 → 冻结配置/隐藏材料/镜像并保留引用 → 原生 Git checkout 完整 commit →
控制器加入 CRLF/Decimal 或 slugify/chunked 回归与用户笔记 → 独立基线验证失败 → 正式
CodePilotApplication 读取/修改/运行公开测试 → 所有任务与后端结束 → 控制器比较基线、保护文件、
Git 与模式 → 新副本只覆盖允许候选文件 → 注入隐藏测试并启动新后端验证 → 原子保存每条结果 →
汇总全部六次，最后释放自己创建的镜像别名。Runtime 或模型自述都不能自行把 verdict 改成 passed。

## 三道理解题与答案

**1. 为什么修复后的 git diff 为空，仍可能是一次真实修复？**

答案：任务起点可能含未提交回归。修复把文件恢复到 upstream HEAD，Git diff 会为空；但与注入后
的用户基线相比，内容已经改变且独立测试由失败变通过。反过来，模型完全没修改且原缺陷仍在，不能通过。

**2. 为什么固定了镜像 ID，还要保留一个临时镜像别名？**

答案：本机更新原标签后，旧 manifest 索引可能失去引用。ID 阻止悄悄切换到新镜像，但不能保证旧索引
仍可寻址。唯一别名维持生命周期，所有 trial 和验证器结束后只删除自己的引用；这次真实失败验证了必要性。

**3. Runtime 是 step_limit，但独立测试通过，应该怎样报告？**

答案：分别记录。代码任务可判独立通过，运行仍记步骤耗尽、没有正常完成；不能将两者改成同一个状态。
请求/Token 和失败轨迹照样保留。即使所有样本通过，也不代表网络/秘密、磁盘或安全撤销等发布阻断消失。

材料由 AI 交付，用户理解程度待确认；没有动手题，也不将这些材料当作用户独立贡献证明。

安装阅读补充：scripts/check_wheel.py 按内容和路径核对 wheel 与源码，防止最后编辑晚于构建。
本轮确实在安装测试中发现旧包，重建后才验收；不能只看版本仍是 0.1.0 就认定安装了最新实现。
