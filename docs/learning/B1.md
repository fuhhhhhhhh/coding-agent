## 一次执行轨迹

会话重开并核验 → 加载可靠历史和引用 → 新建 run → 既有 Runtime/权限/调度 → 工具执行时分块持久输出 → 配对结果与终态持久化 → 关闭执行资源但保留历史 → 下一条输入继续。副作用未知在请求模型或重放工具前阻断。以上是目标轨迹，当前实现尚不支持完整链。

## 三道理解题及答案

### 1. 为什么把输出和持久会话放在同一大阶段？

输出引用的所有者应是可保留的会话。若只做 run 内输出，再单独做持久化，很容易在 run 清理时删掉仍需要的正文。联合设计可以同时核对配额、索引、生命周期和重开访问。

### 2. 重开会话为什么不等于重新运行上次工具？

上次可能已写入或 commit，只是结果没持久化。加载历史提供继续工作的依据，不证明执行未发生；未知调用先协调，旧 run 终态不改变，新任务创建新 run。

### 3. 大阶段交付是否意味着可以省略故障验证？

不能。内部细项变为联合验收清单，开发可以连续推进；只有正常对话、重开、取消、配额、崩溃和清理均有独立证据才能完成整个阶段。多个内部提交或新增几个模型类都不能代替产品链通过。
