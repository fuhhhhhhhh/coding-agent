## 阅读入口

1. runtime/loop.py::Runner.run：状态、总时限、取消与最终报告。
2. Runner._loop：历史更新、顺序调用、结果回传、额度检查。
3. Runner._track_failure：与 ID 无关的签名和连续计数。
4. fixtures/m02.py::FixtureExecutor.execute：固定参数边界及真实测试进程。

以上代码均在 src/codepilot 中。契约为 contracts/run.py；场景编排为
m02_demo.py::run_scenarios；行为验证入口为 tests/test_runtime.py。

## 一次正常轨迹

运行 `uv run --locked python -m codepilot.m02_demo`，对照 docs/evidence/M02-repair.jsonl 的 15 条记录：

1. step 1 请求与回复：assistant 要求 read_file(read-1)。
2. 工具请求与结果：读取临时 calculator.py，内容仍是错误减法。
3. step 2 请求包含前面的调用及配对结果，回复 write_file(write-1)。
4. 写入加法实现，结果以同一 write-1 回传。
5. step 3 请求含读写历史，回复 run_tests(test-1)，实际 unittest 返回 exit_code=0。
6. step 4 请求含全部结果，回复不再带工具调用。
7. run_stopped 为 completed，报告 steps=4、tool_calls=3。

演示额外检查文件内容和实际测试结果，再清理临时副本；原错误 fixture 保留以便复现。

## 三个核心机制的解释

**模型结束与强制停止。** 无调用的合法回复使循环正常结束。
步数、额度、时间或重复失败达限后，即使 fake 还有回复，Runner 也不再继续。
M02-step_limit.jsonl 只有两次请求与调用；M02-baseline.jsonl 则显示 completed 与
exit_code=1 可以同时出现。因此模型结束、循环受控停止、任务成功有不同的判据。

**错误如何进入下一次请求。** 未知工具、错误参数及普通工具异常变为
ToolResult(is_error=True)，携带原 call_id，包装成 tool Message 加入历史。
下一次 complete 看到这些信息，允许纠正。Provider 请求本身失败时，本轮直接终止，
不把网络重试和副作用工具重试混成一件事。

**状态由谁管理。** Runner 拥有本次历史、额度、失败签名和终态；
provider 只返回模型回复，executor 只执行一次调用。run_id/sequence 关联轨迹，
call_id 关联结果，step 关联模型请求。组件收到副本，避免修改嵌套参数污染历史。
永久会话、恢复执行和流式状态仍未实现。

## 故障证据

| 文件或测试 | 行为 |
| --- | --- |
| M02-repeated_failure.jsonl | 同一未知工具失败三次后停止，不受 call_id 变化影响 |
| M02-tool_exception.jsonl | 工具异常成为错误反馈，模型收到后正常结束 |
| M02-provider_error.jsonl | 首次模型请求失败，记录异常类型后终止 |
| M02-argument_error.jsonl | 缺 content 的写请求被拒绝，没有修改文件 |
| M02-tool_budget.jsonl | 零额度拒绝调用，工具尝试数为零 |
| M02-time_limit.jsonl / M02-cancelled.jsonl | 超时与取消分别产生唯一终态 |
| test_fixture_test_process_is_reaped_on_timeout | 挂起的直接测试进程被回收，无后续调用 |

轨迹均位于 docs/evidence。取消中的调用可能没有结果，这不代表它可以安全恢复重放。

## 注释如何阅读

每个函数开头的中文 docstring 先回答“这个函数负责什么”；函数体内分支前的中文注释再回答
“为什么要在这里拒绝、停止、转译错误或清理资源”。建议先只读 `Runner.run` 的 docstring
和异常分支注释，再读 `_loop` 的模型回复、额度、执行和 ID 配对四段，最后对照 JSONL。
注释不替代测试和设计文档：docstring 是局部职责，M02.md 是跨函数状态与边界。
