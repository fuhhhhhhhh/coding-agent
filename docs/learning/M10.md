# M10 学习记录：Artifact 引用、Prompt 视图与原子回合压缩

## 推荐阅读顺序

你已有 CoreCoder、Runtime、工具、调度和 Docker 基础，不需要逐文件通读。沿两条数据流阅读：

1. `src/codepilot/context/models.py`：先确认预算、artifact、摘要和 prompt 视图分别是什么，避免把它们混成一份“上下文对象”。
2. `src/codepilot/context/artifacts.py`：读 `write`、`read`、`cleanup`，理解原文的所有权和生命周期。
3. `src/codepilot/context/manager.py`：第一遍只读 `execute`、`prepare`、`_artifact_prompt` 和 `_split_atomic_rounds`。
4. `src/codepilot/runtime/loop.py`：看 `_loop` 请求 Provider 前如何取得 `ContextView`，以及失败为什么不增加 step。
5. `src/codepilot/context/summarizer.py`：看摘要 Provider 为什么是独立无工具请求，usage 如何返回。
6. `src/codepilot/context/assembly.py`：看仓库规则和任务为何成为受保护前缀，代码文件为何仍用 glob/search/read_file 按需读取。
7. `tests/test_context.py`：按“大输出→读取→压缩→故障”顺序核对承诺。
8. 最后运行 `python -m codepilot.m10_demo`，对照基础策略和治理策略的相同任务结果与估算 Token。

`__init__.py` 只是公开接口，第一遍可跳过。`contracts/stream.py` 和 `contracts/run.py` 只增加事件字段与 `context_limit`，理解主流程后再看。

## 一次执行轨迹

```text
Runner 准备第一次 Provider 请求
  -> ContextManager.prepare：低于阈值，原样发送规则与任务
Provider 请求 collect_logs
  -> ContextManager.execute
  -> 下游工具返回 110KB 原文
  -> ArtifactStore 写入 0600 文件并计算 SHA-256
  -> Runner 历史只追加短 ToolResult 引用
Provider 从短引用看到中段错误线索
  -> 请求 read_context_artifact(start=错误附近位置)
  -> controller-owned store 返回有界片段
Provider 给出最终结论
```

多轮任务接近预算时，`prepare` 先把历史分为“不可删除前缀、旧完整回合、近期完整回合”，只将旧完整回合交给摘要器。Provider 获得的是 prefix + summary + recent；RunReport 仍是逐条原始历史。

## 与 Claude Code 风格靠齐的地方

- 仓库规则持续存在，不因为历史变长被普通摘要替换。
- 代码和大输出按需读取，避免一次把全部材料塞入 prompt。
- 自动压缩与手动 compact 使用同一机制，压缩是可观察的有损操作。
- 工具输出引用带来源、范围和继续读取方式，而不是只写一句“内容太长”。
- 失败时给出明确停止原因，不静默丢失约束或伪装成无限上下文。

这些是公开交互原则。本项目的分组算法、artifact 协议、预算估算和事件契约是当前仓库自己的实现。

## 三个设计取舍

第一，artifact 放在控制器私有目录，而不是工作区。这样 Agent 不能通过普通写文件工具篡改原始证据；代价是需要专门的只读工具，并且跨进程索引恢复还没实现。

第二，压缩以 assistant 调用和全部 tool result 为原子。这样不会留下“模型请求过工具但结果消失”或“孤立工具结果”；代价是一个很大的近期回合可能导致清晰停止，而不能任意从中间裁剪。

第三，规范历史和 prompt 视图分开。这样审计仍能看到真实执行顺序，下一轮模型只承担有预算的视图；代价是调试时必须明确自己正在看 `RunReport.messages` 还是 `ContextView.messages`。

第四，摘要调用有独立墙钟总时限。SDK 的连接或单次读取超时不一定覆盖整个流；真实 DeepSeek 复验中，连接建立后长时间没有可用分片。`ModelSummarizer` 因而在完整收集过程外再包一层总时限，超时后由 ContextManager 转成清晰的 `summary_failed:TimeoutError`，不会让 Agent 无限等待。

## 理解题与答案

### 1. 为什么 artifact 写入失败时不能仍然返回短引用？

因为短引用承诺原文可以按需取回。如果文件没有成功持久化，返回引用等于删除唯一工具结果，并在后续读取时制造不可恢复的悬空 ID。当前实现保留原始 ToolResult，再由预算层决定它是否还能安全进入 prompt；若不能则明确停止。

### 2. 为什么压缩不能只按消息数量删除最老的若干条？

assistant 消息中的工具调用和后续 tool 消息通过 call ID 构成协议单元。只删其中一部分会让 Provider 收到无结果调用或孤立结果，既可能被 SDK 拒绝，也可能让模型误判工具是否执行。`_split_atomic_rounds` 先验证配对，再以整个组为压缩单位。

### 3. 为什么本地 Token 估算和 Provider usage 都要保留？

请求前必须有一个无需网络的估算才能决定是否压缩和预留回答空间；请求后 Provider usage 才是该模型实际计量。估算器跨模型有误差，Provider 又可能不返回 usage，因此两者通过 `source` 分开记录，不能用估算冒充账单，也不能把未知当作零。

## 当前边界

M10 的 fake 摘要验证了控制流、配对、预算和故障处理。2026-10-15 的真实 DeepSeek 复验确认认证、模型可用性和超时停止，但两次生成均未在时限内得到完整摘要，因此仍没有证明真实摘要质量。Artifact 索引不能跨进程恢复，磁盘目录没有硬配额；这些能力分别属于后续会话恢复和部署存储策略。当前代码检索继续使用 glob/search/read_file，没有引入向量数据库。
