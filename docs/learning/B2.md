## 三道理解题及答案

### 1. 为什么不把 Shell 工具的 effect 改成 read？

Shell 仍可启动任意进程、访问网络或修改文件，工具声明必须保留 `process`。只有具体调用通过严格 Action 识别时才自动放行，未知调用仍受审批保护。

### 2. 什么样的 `&&` 组合可以自动放行？

只有每一段都独立通过严格查询白名单、且连接符只有 `&&` 时才自动放行。`pwd && ls -la` 可以通过；只要混入 `git commit`、网络命令或其他 Shell 语法，就必须审批。

### 3. 为什么斜杠命令要在 CLI 外壳处理？

`/help`、`/status` 等是会话控制操作，不应消耗 Provider 请求、创建任务或被模型解释。外壳处理也使未知命令可以立即纠正，并保持 Runtime 不依赖 UI。

### 正常执行轨迹

正式任务读取并修改文件 → 调度获得文件写资源 → 控制器保存原始脏字节与 intent → 原后端执行带版本条件的文件工具 → 核对实际内容等于预计目标后确认 → 后端关闭 → sealed。用户先 changes 审查，再 undo --apply；会话进入 needs_reconciliation 防崩溃，全部当前版本匹配后逆序恢复原始脏内容，最终提交 undo_settled。非 Git 目录也走此链。

### 三道理解题及答案

1. **为什么不能拿整个工作区的 before/after 差异直接撤销？** 期间可能混入用户、Shell、后台和扩展的修改。基线能证明变化，不能证明归属。本轮只认领明确文件工具成功且实际结果匹配预计字节的修改；未知或外部版本变化时拒绝撤销。
2. **为什么审批返回后检查一次还不够？** 工具可能在调度队列等待，期间批准过期、管理员替换策略或目录被替换。ContextVar 传递本次复核函数，在实际获得执行槽时重核，退出恢复，不能复用另一调用的授权。
3. **为什么容器里提交成功后仍要比较固定 base？** status 只显示相对 HEAD 的未提交修改，commit 会把它清空，但任务仍改变了相对初始 commit 的文件。交付必须比较初始 base，并在全新起点重放补丁和独立测试，才能保护源分支并证明补丁有效。

边界：Local 环境过滤不等于宿主沙箱；Shell/扩展变更、删除/重命名、ACL/xattr 不由本轮文件工具撤销认领。Docker 独立 Git 当前要求仓库根目录；没有受控联网/秘密注入或真正硬工作区配额，不能宣布成熟发布。日志正文沿会话 TTL/delete 清理，新增 run 日志不能追溯补齐旧任务。

补充阅读 `src/codepilot/evals/verifier.py::IndependentVerifier.verify`：理解为何验证器也要沿明确后端、限制环境与输出并负责清理；`GitTaskWorkspace.finish` 在清理不确定时保留 replay，不能用本机命令成功冒充容器验证。

一次正常轨迹：用户显式选择限容模式 → 会话锁内预留产物额度 → 复制真实脏文件 → 创建 tmpfs 容器并登记 ID → read_file 返回分页和文件版本 → edit_file 用真实读取版本修改一批文件 → 容器检查点 → Runtime completed → 最终停止写入并导出 → 删除已保存产物的容器 → 整批核验源版本 → 逐文件交付并记录进度 → 返回交付状态。若用户中间修改源文件，产物留在私有目录，源目录不会被整批覆盖。

三道理解题与答案：

1. **已经读过第一页，为什么下一页还要携带 SHA-256？** 字节游标只对同一文件版本有效。文件中间插入一行后，原偏移可能指向另一个内容；每页完整有界扫描并校验版本，才能防止拼出一个从未存在过的文件。
2. **多文件编辑为什么既要预检查，又要记录 applied/failed/unattempted？** 预检查可避免第二个文件明显冲突时先修改第一个；真正执行中磁盘满或用户并发修改仍可能出现。文件系统没有跨文件原子事务，因此必须保留真实部分进度，不能用总错误掩盖已产生的修改，也不能无条件重放。
3. **容器取消后为什么不直接 rm？硬容量限制是否等于持久化？** tmpfs 随停止消失，先删会丢掉唯一的最新产物。先暂停写进程、导出并验证，再删；失败就保留容器和身份。硬限额只限制容量，OOM、主机故障、上次检查点后的丢失仍需区别于可靠持久化。

## 2026-10-20：从断网工具到受控 HTTPS 请求

这次让 Agent 可以在用户批准后读取指定网站，也可以按引用访问需要 Bearer 凭据的指定路径。关键是容器继续断网，秘密留在控制器：模型说“访问哪个 URL、使用哪个引用”，控制器负责判断能否访问、核验真实地址和证书、临时添加凭据，并检查结果后再交给模型。它并没有让任意 Shell 获得网络或用户 API key。

正常轨迹：输入 fetch 或模型发出 http_request → 权限绑定 URL/引用及配置指纹 → 用户批准 → 调度后再复核 → 会话记录请求预留 → 所有 DNS 地址须公开 → 数字 IP 连接、原域名验证 TLS → 若有秘密才临时打开外部私有文件 → 固定 GET → h11 完成消息 → 有界正文检查回显和编码 → 原工具结果/Context/Session 链 → 关闭连接。异常或取消只保留诊断及未知结论，不自动补发。

### 三道理解题及答案

1. **为什么配置允许域名还不够，必须检查 DNS 并连接数字 IP？** 同一域名可能解析到回环、云元数据或私网；只检查名字后再让 HTTP 客户端重新解析还存在重绑定窗口。这里核验全部答案，再连接确定数字地址，TLS 仍验证原域名；下一请求/重定向重新核验。
2. **凭据为什么在 TLS 之后才读取？为什么它仍叫 process？** 证书错误或目的地不符时没有理由读取秘密。通过后再读，并要求路径/文件版本/租期都有效；GET 也可能在服务器产生副作用或把信息发送给外部，所以不是无需审批的本地只读工具。
3. **为什么不能一边读响应一边把正文显示给模型？** 服务可能分块回显秘密，前半段已经发布后就收不回。先在有限内存中收完整响应再检查，超限/截断拒绝，认证错误不回显正文；常见编码过滤仍不能保证检测所有恶意变换，也不能声称透明安装脚本已被安全放行。

实现通过不代表用户已掌握；不布置动手题。原凭据文件由用户管理，代理只限制本次使用范围，不替服务端签发/撤销短期令牌。

补充阅读 `sessions/store.py::finish/reconcile/diagnose` 和 `ui/renderer.py::finished`：请求发送前的持久 pending 与完整响应提交点决定能否继续。工具错误已配对、Runtime completed 都不能清除未知远端结果；普通 --accept-workspace 也不行，要显式 --accept-network-unknown，旧错误和未知事实仍保留。测试 `test_sent_but_incomplete_response_blocks_resume_until_explicit_ack` 用实际 TLS 截断证明该区别，显式 Docker 测试时使用原正式后端。

TLS 阅读补充：在 `_request` 前先看 `system_tls_context`。即使没有读取代理环境，默认 TLS 工厂仍可能信任 `.env` 指定 CA，或因 SSLKEYLOGFILE 将 TLS 会话密钥写入文件。代理显式选择系统信任路径，且不启用日志；对应 `test_workspace_tls_environment_cannot_replace_trust_or_enable_keylog` 实际设置这三个变量，检查测试 CA 未被加载及日志文件不存在。此处改变的是控制器连接的信任来源，不是让容器联网。
