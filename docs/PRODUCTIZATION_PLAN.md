# CodePilot 产品化路线与成熟度门槛

版本日期：2026-10-15

## 目标与完成标准

CodePilot 的目标是成为能够持续处理真实仓库任务的终端 Coding Agent。后续不再用“有类、有单测、有 demo”作为阶段完成标准。每项能力分为四级：

1. **机制实现**：数据契约和核心算法存在，确定性测试通过。
2. **链路集成**：能力进入正式执行链，并与权限、调度、工作区、Trace 和清理生命周期组合。
3. **真实验收**：在受控真实 Provider 或真实执行后端上通过成功与故障场景。
4. **产品就绪**：用户能从统一入口配置和使用，跨长任务稳定运行，失败后可诊断、可恢复或明确停止。

“组件达到三级”和“产品达到三级”必须分开记录。例如 Docker 和任务级 worktree 已通过真实组合验收，但目前没有持久会话入口和恢复机制，所以整个产品执行链仍未达到三级。

## 当前系统离成熟 Agent 还有什么

| 领域 | 当前组件等级 | 已有能力 | 关键缺口 |
| --- | --- | --- | --- |
| 产品入口与配置 | 机制实现 | 分阶段 demo、批量 Harness、基础配置 | 没有统一 `codepilot run/resume`、配置分层、交互事件渲染和完整生命周期 |
| Runtime | 链路集成 | 单 Agent 工具循环、流式、多调用、取消、限额 | Runner 单次使用；无任务状态、恢复、交互式用户转向、共享 Token/费用预算和完成判据 |
| 工具与编辑 | 链路集成 | 六个文件/Shell 工具、原子写、冲突检测、原生 Git CLI 与只读 Git 捷径 | 读取无分页；搜索能力弱；缺补丁事务、PTY/后台任务、结构检索和原始输出流式保存 |
| 权限与秘密 | 链路集成 | allow/deny/ask、预设、审批、审计 | Shell 实际影响不能由工具名/路径规则充分表达；缺网络、环境变量、秘密、会话审批和恢复重验策略 |
| 调度 | 链路集成 | 资源锁、并发上限、FIFO、取消 | 仅进程内；缺全局预算、优先级、背压、后台任务生命周期和跨恢复资源协调 |
| Local/Docker 执行 | 真实验收（组件） | Rootless Docker、断网、只读根、能力删除、资源限制、取消清理 | Local 不是沙箱；bind 工作区无硬磁盘配额；缺镜像供应链、细粒度网络、持久所有权和崩溃后协调 |
| 上下文 | 机制实现 | 大输出引用、消息预算、压缩、按需读取 | 未计算完整请求；无滚动检查点和结构化工作状态；截断前原始输出尚未捕获 |
| 会话与恢复 | 未实现 | JSONL Trace | 无持久会话、快照、资源归属、幂等恢复和 `needs_reconciliation` 流程 |
| Provider | 局部链路集成 | fake、DeepSeek 完整/流式适配、usage 事件 | 正式配置仍只接受 fake；缺能力协商、重试/限流分类、第二协议、统一 Token/费用控制 |
| 可观察性 | 链路集成 | 脱敏 JSONL、执行和上下文事件 | 缺稳定事件版本、会话索引、查询/诊断命令、保留策略和跨组件关联视图 |
| 评测 | 机制实现 | 临时仓库、尝试反馈、独立验证器 | `repository_commit` 未形成可靠 checkout 契约；Diff/快照不覆盖二进制和文件模式；缺固定任务集、重复试验和统计报告 |
| 扩展 | 未实现 | 核心工具注册边界可复用 | 无 Skills、Hooks、MCP；也没有扩展来源、权限、预算和生命周期治理 |
| Git 与任务隔离 | 真实验收 | 固定 commit、独立 worktree、status/diff、二进制 patch、干净重放和归属清单 | 缺自动应用/合并、跨进程清理命令及恢复协调 |
| 安全治理 | 局部 | 路径限制、脱敏、容器基线 | 缺提示注入信任边界、秘密代理、依赖下载策略、安全回归集和沙箱威胁模型 |
| 安装与运维 | 机制实现 | wheel 构建历史证据 | 缺统一命令安装冒烟、版本/迁移、诊断与清理命令、平台支持矩阵 |

当前仓库是“有真实后端和工程约束的 Agent 核心”，不是只有空架子，但也还不是成熟 Coding Agent。主要问题不是某一个模块缺功能，而是这些模块尚未由一个持久任务模型串成产品主链。

## 为什么要改变开发顺序

旧顺序先连续完成四项 Context 加固，再做 worktree、恢复、扩展和 CLI。这个顺序会继续产生孤立的高质量组件，也会让以下问题拖到很晚才暴露：

- 配置对象是否能表达 Provider、沙箱、权限和预算的真实组合。
- 一次任务中的会话、worktree、容器、Artifact 和 Trace 到底归谁所有。
- 取消、崩溃和退出时，各组件的终态能否一致。
- 用户从哪里启动、观察、批准、恢复并取得补丁。

新顺序先建立很薄但正式的产品主链，再逐段加固。每一阶段都必须通过同一个入口和同一个任务模型验收。Context 的四项缺口全部保留，但拆回它们真正所属的层：原始输出捕获属于执行面；完整请求计量同时属于 Provider 与 Context；滚动检查点和结构化状态属于持久会话前置。

## 新的开发顺序

阶段名称描述实际成果，不再把一次提交等同于一个里程碑。现有 M01—M10 编号和历史证据保持不变；下面是从当前状态开始的产品化顺序。

### P1：建立统一产品主链

**状态（2026-10-15）**：已达到真实验收。fake 在 Local 与 Rootless Docker 通过同一 CLI；`qwen3.5-flash` 在 OpenAI-compatible 网关完成流式只读闭环，并在临时仓库完成编辑、Shell 审批和测试闭环。默认 `codepilot` 提供 YAML 自动配置和持续提示符，单次 `run` 供自动化使用；任务间模型历史与持久恢复不属于本阶段。

先实现正式 composition root 和最小 CLI：

- `codepilot run` 从一个配置模型装配 Provider、Context、Permission、Scheduler、ExecutionBackend、Trace 和 Runner。
- 支持 fake Provider 的确定性端到端任务；DeepSeek 只在服务恢复后做受限真实冒烟。
- CLI 只消费 Runtime 事件，不另写执行逻辑；先做清楚的流式文本、工具状态、审批、终态和错误展示，不提前做完整 TUI。
- 配置分为默认值、用户配置、项目配置和命令行覆盖，并在启动前验证不可能的组合。
- 定义稳定 `SessionId/RunId/TaskId` 和一次运行的资源所有权清单，即使此时尚不能恢复。

**故障门槛**：无效配置在产生副作用前失败；Provider 初始化失败仍关闭 Trace/后端；Ctrl-C 传播到模型、排队工具和活动进程，并只产生一个终态。

**完成证据**：从干净 wheel 安装执行 fake 任务；同一路径分别使用 Local 和可用的 Rootless Docker；退出后无活动进程、容器和临时锁。

### P2：直接 Git 工作流与可选任务隔离

- 普通任务直接修改当前目录，兼容未初始化目录和脏仓库；原生 Git 命令由 Shell 在统一权限链内执行。
- 显式隔离任务绑定固定 commit 和独立 worktree，记录创建者、任务、会话、状态和清理条件。
- 增加正式 `git_status`、`git_diff` 和补丁导出能力；Docker 只能使用该任务工作树或它的受控副本。
- 补丁在干净起点重新应用并由独立验证器测试；保留重命名、删除、文件模式和二进制文件的明确边界。
- 有未交付修改、所有权不匹配或路径异常时拒绝自动删除 worktree。

**故障门槛**：起点 commit 不存在、并行任务改同一仓库、补丁无法重放、清理时仍有未保存改动。

**完成证据**：两个并行任务互不污染；导出补丁能在新的干净 worktree 重放并复验。

### P3：加固受控执行面

这一阶段同时处理沙箱、Shell、Artifact 和权限，因为它们共同决定副作用边界。

- ExecutionBackend 提供 controller-owned `OutputSink`，在任何预览截断前流式保存 stdout/stderr；支持有界读取和搜索。
- 为单 Artifact、单命令、单任务和整个会话设置字节/时间/进程预算；超限留下 `partial` 或 `quota_exceeded`，不假装完整。
- 明确 Local 是可信宿主执行模式；Docker 才提供当前声明的隔离保证。补充磁盘消耗控制、镜像 ID/来源/更新策略和过期资源协调。
- 权限从“工具名匹配”升级为规范化 `Action`：文件范围、命令、网络、环境变量、秘密、执行后端和预计副作用进入同一次判定。
- 审批绑定完整 Action、会话和有效期；恢复后重新核验。秘密通过受控注入进入进程，不进入 Prompt、Trace 或普通工具结果。
- Shell 增加输出 spooling；PTY、交互命令和后台任务只有在生命周期协议明确后再启用。

**故障门槛**：超过 100MB 的交错输出、磁盘/Artifact 配额耗尽、容器被强杀、审批后参数改变、Shell 尝试绕过文件工具路径策略、秘密出现在输出中。

**完成证据**：内存保持有界，中段输出可检索；权限日志能解释实际 Action；取消和控制器重启后能够发现并协调遗留资源；公共 Docker 环境不受影响。

### P4：把上下文变成有界、可核验的工作状态

- Provider 提供 `ProviderCapabilities` 和 `RequestBudgetReport`，计算消息、工具 Schema、协议固定开销、回答预留和误差余量。
- ContextManager 使用完整请求预算决定通过、压缩或停止；已知超限请求不得发送。
- `CompactionCheckpoint` 只用“旧摘要 + 新增完整回合”滚动更新，摘要失败时原子保留旧检查点。
- 引入严格 `WorkingState`：目标、不可违反约束、待办、修改文件、测试结果、错误、风险和来源消息 ID。
- 初始用户目标与仓库规则由控制器确定性保留；模型摘要必须通过结构和来源校验，不能自行伪造测试通过。
- Prompt 视图、规范事件历史、原始 Artifact 和结构化状态继续分离。

**故障门槛**：短消息配巨大工具 Schema、连续百回合压缩、摘要超时/非法 JSON/伪造来源、单条消息超过硬上限、工具调用和结果跨压缩边界。

**完成证据**：请求预算可解释；摘要输入规模有界；约束和验证结论可追溯；固定长任务中至少三次压缩仍能完成搜索、修改、失败测试、修复和独立验证。

### P5：持久会话与保守恢复

- 使用追加事件日志保存事实，SQLite 只保存索引、状态、资源归属和快照；Schema 有版本和迁移策略。
- 持久化 WorkingState、压缩检查点、Artifact 索引、预算、审批摘要、worktree/容器/进程归属和最后可靠事件位置。
- 工具状态至少区分 `planned/running/succeeded/failed/cancelled/unknown`；不能确认副作用结果时进入 `needs_reconciliation`。
- `codepilot resume` 先协调资源与权限，再重建 Prompt；不会盲目重放写操作。

**故障门槛**：模型请求前、工具副作用中、工具完成但状态未提交三处崩溃；SQLite 写失败；JSONL 尾部截断；工作树或容器被外部修改。

**完成证据**：每个崩溃点都有唯一、可解释恢复结果；已取消终态不会复活；人工协调项在 CLI 中可见。

### P6：Provider 可靠性和预算治理

- 正式配置启用 DeepSeek，并接入第二种协议；SDK 类型不泄漏到核心层。
- 能力表覆盖上下文窗口、最大输出、流式、工具调用、并行调用、usage、推理字段和 tokenizer 来源。
- 区分认证、余额、限流、超时、服务端错误、协议错误和上下文超限；只对安全请求采用有界退避并尊重 `Retry-After`。
- 会话统一限制请求数、输入/输出 Token、估算费用和墙钟时间；Provider 的未知 usage 显式保留未知。
- 模型终止不等于任务完成，最终结果仍由任务判据或独立验证器确认。

**故障门槛**：429、断流、重复增量、usage 缺失、工具参数不完整、请求已被服务端接受但客户端超时、模型宣称完成而验证失败。

**完成证据**：两个协议通过同一 mock 契约套件；服务可用时各做受限真实冒烟；真实故障与 mock 通过分开报告。

### P7：扩展系统与高级任务能力

- Skills 采用元数据发现和按需加载，正文不默认全部注入。
- Hooks 有阶段、超时、失败策略、输入输出 Schema 和执行环境声明。
- MCP 工具使用命名空间，仍经过参数校验、权限、调度、输出治理、Trace 和恢复边界。
- 后台任务先于子 Agent：先定义任务状态、事件消费、取消和产物，再增加受限 explore/review/coder 子 Agent。
- 子 Agent 继承父权限和共享预算，拥有子额度和深度限制，只向主任务返回结构化结论和证据引用。

**故障门槛**：恶意工具描述、MCP 断开/重连、Hook 卡死、同名工具、后台通知重复、子 Agent 超预算或试图扩大权限。

**完成证据**：扩展不能绕过统一执行链；禁用扩展后核心任务仍可运行；所有外部副作用都有归属和审计。

### P8：产品交互、评测与发布

产品交互在 P1 已有骨架，此阶段补齐成熟使用体验：

- `/status`、`/diff`、`/test`、`/context`、`/compact`、`/permissions`、`/cancel` 和诊断/清理命令。
- 任务集覆盖单文件、跨文件、仓库探索、长上下文、失败反馈、恢复和安全边界；仓库 commit 与环境可复现。
- 每个关键配置重复运行，报告逐次结果、均值、波动、Token、费用、耗时和失败分类。
- 加入提示注入、路径/符号链接、Shell、秘密泄漏、MCP 和沙箱逃逸假设的专项安全回归。
- 从干净 wheel 安装验收；声明 Python/OS/Docker 支持矩阵、数据库迁移、日志保留和已知限制。

**完成证据**：统一入口完成真实仓库任务；Local 与 Rootless Docker 的能力差异清楚；至少两个 Provider 协议有可追溯证据；发布文档中的每项声明能对应代码、测试或真实运行记录。

## 持续评测，不把质量拖到最后

P8 负责正式汇总，不表示前面可以等到最后才评测。从 P1 起，每一阶段都维护同一组小型回归任务：

1. 只读定位问题并给出证据。
2. 单文件修改并通过独立验证。
3. 跨文件修改，先失败再根据测试反馈修复。
4. 长输出和长历史任务。
5. 取消、超时、权限拒绝和资源清理。

每次能力升级都在这些任务上比较成功判据、运行时间、请求数、Token、Artifact、残留资源和失败分类。只有数据契约变化时更新基准定义，不能为了让新实现通过而静默降低判据。

## 成熟产品必须满足的横向不变量

无论处于哪个阶段，以下约束始终成立：

- 一个 run 只有一个最终终态；终态后不再启动模型或工具。
- 所有副作用都能追溯到 task、run、tool call、权限判定和工作区。
- 规范历史、Prompt 视图、结构化状态和 Artifact 各有唯一所有者，不能相互覆盖。
- 用户取消传播到 Provider、调度队列、活动进程、容器和后台任务。
- 无法确认是否发生副作用时停止自动重试，进入协调状态。
- Local、Docker、worktree 和权限分别陈述，不能用其中一项代替另一项的保证。
- 用户输入、仓库内容、工具输出和远程扩展都视为不可信数据，不能把其中的指令自动提升为系统权限。
- 测试通过、模型自述和独立任务完成判据必须分开记录。
- 日志默认不含 Prompt、工具正文、宿主路径和秘密；需要诊断正文时由用户显式开启受控范围。

## 每个增量的固定交付

每个增量必须同时交付：

1. 数据契约、状态所有权和资源生命周期说明。
2. 正常链路、至少三个重要故障场景和可观察事件。
3. 确定性测试，以及适用时的真实后端或 Provider 测试。
4. 通过统一产品入口运行的集成场景；P1 完成前使用临时入口时必须明确标注。
5. 设计说明、学习记录、证据和准确的成熟度等级。
6. 描述实际行为的 Git 提交和推送。

代码量、文件数量和 demo 输出都不是完成证据。交付必须回答：用户从哪里启动，状态由谁持有，权限在哪里决定，副作用发生在哪里，失败后留下什么，如何继续，以及怎样独立确认任务已经完成。
