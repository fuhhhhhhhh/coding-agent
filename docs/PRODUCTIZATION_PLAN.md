# CodePilot 产品化路线与成熟度门槛

版本日期：2026-10-15

## 目标重新定义

CodePilot 的目标是成为可以持续用于真实仓库的终端 Coding Agent，而不是把若干机制演示拼在一起。后续不再用“有类、有单测、有 demo”作为阶段完成标准。每项能力分为四级：

1. **机制实现**：数据契约和核心算法存在，确定性单元测试通过。
2. **链路集成**：能力接入真实 Runner、权限、调度、工作区、Trace 和清理生命周期。
3. **真实验收**：在受控真实 Provider 或真实执行后端上通过成功与故障场景。
4. **产品就绪**：可以从统一 CLI 配置和使用，跨多轮任务稳定运行，有恢复、诊断和明确边界。

文档中的“完成”必须注明是哪一级。只有第 4 级才能称为成熟产品能力；第 1 级或单个 demo 不能再写成整个阶段完成。

## 当前判断

| 领域 | 当前等级 | 已有证据 | 距离产品就绪的主要缺口 |
| --- | --- | --- | --- |
| Runtime 与工具循环 | 链路集成 | 非流式/流式、停止、取消、调用配对 | 统一交互 CLI、长任务恢复、跨 Provider 能力协商 |
| 文件与 Shell 工具 | 链路集成 | 路径限制、原子编辑、进程树清理 | 执行端原始输出流式落盘、真实仓库长期使用验证 |
| 权限与调度 | 链路集成 | allow/deny/ask、审批、资源锁、取消 | CLI 会话中的可解释审批、策略配置和恢复后重验 |
| Docker 工作区 | 真实验收 | Rootless Docker live 测试 | 与 worktree、会话恢复和正式任务入口完整组合 |
| 评测 Harness | 机制实现 | fixture 任务、独立验证、纠错 | 固定任务集、重复试验、真实模型、正式报告 |
| 上下文治理 | 机制实现 | 大输出引用、预算、原子压缩、故障测试 | 本文下一节的四项加固、真实摘要成功、长会话压力测试 |
| 会话与恢复 | 未实现 | 只有内存历史和 JSONL Trace | SQLite 状态、快照、崩溃协调、needs_reconciliation |
| 扩展与多协议 | 未实现/局部 | 一个 DeepSeek 适配器 | Skills、Hooks、MCP、第二真实协议和能力矩阵 |
| 终端产品入口 | 未实现 | 分阶段 demo 与批量入口 | 一个统一命令、会话命令、配置、错误展示和安装验收 |

因此，当前仓库是有工程约束的 Agent 核心，不是成熟 Coding Agent。M01—M10 的证据仍有效，但表示相应组件达到的等级，不再推导为整个产品已经成熟。

## 立即执行：上下文产品化加固

以下四个增量从下一次开发开始连续完成，全部位于 M11 worktree 之前。提交标题描述实际行为，不使用只有阶段编号的标题。每个增量都要更新 M10 设计、学习记录、状态和证据。

### 增量一：计算完整 Provider 请求预算

**问题**：当前只估算 `Message` JSON，没有计算工具 Schema、Provider 包装、系统前缀、图片或协议固定开销。错误估算可能让压缩触发过晚，最终由 Provider 拒绝请求。

**实现契约**：

- 新增 `ProviderCapabilities`：模型 ID、上下文窗口、最大输出、是否有精确 tokenizer、协议开销策略。
- 新增 `RequestBudgetReport`：消息、工具 Schema、固定开销、回答预留、误差余量和总量分别记录。
- Provider 暴露 `estimate_request(messages, tools, reserve)`；没有精确 tokenizer 时明确返回 `estimate` 来源和保守余量。
- ContextManager 根据完整请求报告决定通过、压缩或 `context_limit`，不能只看消息正文。
- 工具目录变化后重新计量，避免启用 MCP/Skills 后 Schema 膨胀而预算不变。

**故障实验**：

- 消息很短但工具 Schema 很大，必须提前压缩或停止。
- 回答预留超过模型上限，Provider 请求次数必须为零。
- Provider 能力未知时使用保守配置并记录降级，不能假装精确。

**退出门槛**：固定 Provider fixture 下本地估算与协议 tokenizer 的误差在声明范围内；Trace 能解释每一类 Token 占用；Runner 不发送已知超限请求。

### 增量二：建立滚动压缩检查点

**问题**：当前规范历史不断增长；旧历史集合变化后会重新摘要更长输入，成本随会话增长，摘要请求本身最终也会超限。

**实现契约**：

- 新增 `CompactionCheckpoint`：覆盖到的规范消息序号、旧摘要、来源哈希、结构化工作状态、累计摘要 usage。
- 下一次压缩只输入“上次摘要 + 新增完整回合”，不重复发送已经压缩的原始历史。
- 检查点只有在新摘要完整校验并落盘后才替换；失败继续保留旧检查点。
- 规范事件日志仍保存事实顺序，Prompt 视图从检查点生成；两者的所有权继续分离。
- 限制单次摘要输入和累计压缩次数，避免递归摘要无限漂移。

**故障实验**：

- 连续 100 个工具回合多次触发压缩，摘要输入规模保持有界。
- 摘要中途超时或进程取消，旧检查点仍可使用，不出现半更新。
- 工具调用与多个结果跨阈值时整体保留，不能拆组。

**退出门槛**：长历史测试证明新增一次回合不会重新摘要全部旧历史；摘要 Token 成本随新增量增长；取消、失败和缓存恢复都有可观察记录。

### 增量三：使用结构化工作状态并核验关键事实

**问题**：自由文本摘要可能遗漏约束或把推测写成事实，现有提示词无法机械验证。

**实现契约**：

- 新增严格 `WorkingState`：用户目标、不可违反约束、待办、已修改文件及摘要、测试命令与结果、已知错误、未解决风险、来源消息 ID。
- 初始用户目标和仓库规则由控制器确定性复制，不交给模型决定是否保留。
- 摘要模型只归纳历史产生的变化；输出必须经过 Pydantic 校验和来源 ID 校验。
- 合并规则逐字段定义：约束只能显式解除，待办有 open/done 状态，测试结果不能被后来叙述静默覆盖。
- 自由文本只作为模型阅读视图；控制逻辑依赖结构化字段。

**故障实验**：

- 模型遗漏约束、返回未知来源 ID、伪造测试通过或输出非法 JSON，检查点不得提交。
- 同一文件多次修改和测试先失败后通过，最终状态保留时间顺序和最后可信结论。
- 摘要器失败时保留近期回合与旧检查点，并明确停止或降级。

**退出门槛**：所有关键约束都有可追溯来源；测试与修改状态可以机械检查；故意损坏的摘要不能污染下一轮 Prompt。

### 增量四：在执行端截断前流式保存原始输出

**问题**：ContextManager 位于工具返回之后；Shell 或后端若先截断输出，后续 Artifact 只能保存已经丢失的片段。

**实现契约**：

- ExecutionBackend 支持 controller-owned `OutputSink`，stdout/stderr 在产生时写入临时 Artifact。
- ToolResult 返回流别名、总字节数、截断预览、退出码、校验和与 Artifact ID，不把宿主路径暴露给模型。
- `read_context_artifact` 支持按范围读取；增加有界 `search_context_artifact`，定位不依赖少数英文错误关键词。
- 设置单 Artifact、单运行和目录总容量；超限要停止写入并记录 `partial/quota_exceeded`，不能假装保存完整。
- 正常结束执行 fsync 和原子发布；取消、崩溃和磁盘失败有明确的部分文件清理或保留策略。

**故障实验**：

- stdout/stderr 交错且超过内存预览限制，任意中段标记仍可搜索和读取。
- 进程取消、磁盘写满、超过 Artifact 配额时，工具终态与保存完整性标记一致。
- Docker 内工具输出留在控制器侧 ArtifactStore，容器不能篡改已发布证据。

**退出门槛**：真实 Shell 产生超过 100MB 输出时控制器内存保持有界；中段内容可定位；清理后无孤立临时文件；Trace 不记录正文和宿主路径。

### 上下文成熟度总门槛

四个增量通过后仍需一次集成验收，才能关闭 M10 产品化加固：

- 在固定真实仓库执行至少 50 个模型回合，触发大输出落盘和至少三次滚动压缩。
- 同一次任务经历搜索、编辑、测试失败、修复和最终独立验证，用户约束与修改/测试状态始终可追溯。
- 比较无治理与治理配置的任务结果、完整请求 Token、摘要成本、耗时和失败分类。
- 注入摘要超时、磁盘配额、进程取消和损坏摘要，均产生唯一终态且可恢复或明确停止。
- DeepSeek 恢复后运行一次成功 live 摘要；随后用第二协议重复关键契约，避免把 Provider 特性写进 ContextManager。

在该门槛通过前，`docs/STATUS.md` 必须写“上下文机制实现/产品化验收未完成”，不能写“M10 完整完成”。

## 后续产品化顺序

### 任务隔离与补丁交付

完成上下文加固后进入现有 M11：每个任务绑定固定起点和独立 worktree；Docker 使用对应工作树；状态、Diff、补丁导出和清理统一归属。验收必须通过两个并行真实任务以及补丁在干净仓库的重新应用，不能只调用 Git 命令做演示。

### 持久会话与崩溃恢复

现有 M12 负责 SQLite 事件索引、快照和 `needs_reconciliation`。它同时持久化滚动摘要检查点和 Artifact 索引。至少在模型请求前、工具副作用中、工具完成但状态未提交三处注入崩溃，恢复不能盲目重放写操作。

### 扩展系统仍经过核心边界

现有 M13 的 Skills、Hooks、MCP 分别验收。任何扩展工具都必须经过 Schema 校验、权限、调度、上下文输出治理和 Trace；扩展不能绕过 Docker 工作区或把正文无限注入 Prompt。

### 第二协议与能力协商

现有 M14 不只做字段转换，还要实现 Provider 能力表、完整请求计量、结束原因、usage、上下文上限、工具能力和错误分类。每个协议需要 mock 契约测试与真实冒烟；真实服务故障时记录外部阻断，不能把 mock 结果写成真实兼容。

### 统一终端产品入口

正式评测前必须有一个统一 CLI，而不是继续增加分散的 `mXX_demo.py`：

- `codepilot run`：选择工作区、Provider、模型、权限预设和 Local/Docker 后端。
- `codepilot resume`：恢复会话并展示待协调副作用。
- `/context` 与 `/compact`：查看预算组成、检查点和手动压缩。
- `/status`、`/diff`、`/test`：查看任务状态、补丁和验证结果。
- `/permissions`：解释当前规则和下一次审批的实际参数。
- `/cancel` 与正常退出：传播取消并清理进程、容器、锁和临时 Artifact。

CLI 必须消费 Runtime 事件，不能另写一套执行逻辑。完整 TUI 可以后置，但成熟终端 Agent 不能只有模块 demo。

### 正式评测与发布门槛

现有 M15 在以下条件满足后才开始：

- 从干净安装启动，不依赖开发仓库的隐式环境。
- 至少两个真实 Provider 协议通过受限冒烟。
- Local 与 Rootless Docker 均能完成统一任务入口。
- worktree、恢复、上下文、权限和验证器已经在同一端到端任务中组合。
- 固定任务集覆盖单文件、跨文件、长上下文、失败反馈、恢复和安全边界。
- 关键配置重复运行，报告每次结果、均值、波动、Token、费用、耗时和失败分类。

发布时区分：组件测试通过、集成通过、真实环境通过、平台未验证。简历只写有代码和运行证据的能力。

## 每个后续增量的固定交付

每个增量必须同时交付：

1. 内部数据契约和状态所有权说明。
2. 正常链路、至少三个重要故障场景和可观察事件。
3. 确定性测试，以及适用时的真实后端/Provider 测试。
4. 一个通过统一产品入口运行的集成场景；统一 CLI 尚未完成前，要记录这是临时入口。
5. 设计说明、学习记录、证据文件和准确状态等级。
6. 描述实际行为的 Git 提交和推送。

代码量、文件数量和 demo 输出都不是完成证据。完成证据必须回答：用户从哪里启动、状态由谁持有、失败后留下什么、能否继续、如何核对任务真的完成。
