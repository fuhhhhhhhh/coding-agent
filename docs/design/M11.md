# M11 / P2 设计：直接 Git 工作流与可选 worktree 交付

## 范围与产品行为

产品默认直接在启动目录运行。这符合交互式 Coding Agent 的主要使用方式：未初始化目录可以直接编辑或
执行 `git init`，脏仓库继续保留用户已有修改，Agent 的结果也立即出现在用户正在查看的目录。Git 不再
复制实现一套子命令工具；模型通过既有 `shell` 调用原生 Git，因此 commit、branch、fetch、pull、push
使用 Git 自己的完整参数语义，并统一经过 `process` 权限、调度、超时、取消和 Trace。

任务级 worktree 仍是有价值的显式隔离工作流。传入 `--worktree` 或配置 `git_workspace.enabled: true`
后，产品从固定 commit 创建 detached worktree，并保留原有补丁重放与独立复验。该模式默认不要求源
目录干净，但源目录未提交内容不会进入固定 commit；重视严格可复现起点的项目可打开
`require_clean_source`。本阶段没有自动合并、后台任务、会话恢复或多 Agent。

## 数据契约与所有权

`GitWorkspaceConfig` 保存可选隔离状态、起点、源目录干净要求、固定验证 argv、验证时限和补丁大小上限。
`GitTaskWorkspace` 拥有两个路径：Agent 修改的 `worktree/` 和短暂存在的 `replay/`。控制器在
`workspace.json` 记录当前 UID、session/task/run ID、源仓库、固定 commit、工作树路径、状态和补丁
摘要；文件权限为 `0600`。

`GitDelivery` 进入 `ProductRunResult`，明确区分：

- `cleaned`：任务没有修改，worktree 已安全移除。
- `changes_retained`：补丁已导出并在干净起点重放，可选验证也通过。
- `failed_retained`：运行、重放或独立验证失败，原 worktree 和补丁继续保留。

有修改的任务不会被自动删除。显式 `cleanup()` 还会重新核对清单 UID、task ID、绝对路径和当前 Git
状态；只要还有任何修改就拒绝清理。

## 补丁与复验

交付使用 Git 自己的二进制 patch 格式，而不是文本快照。控制器创建临时 index，读取固定 commit，
用 intent-to-add 纳入未跟踪文件，再执行禁用 external diff 和 textconv 的 `git diff --binary
--full-index --find-renames`。因此新增、删除、文件模式和二进制内容都进入同一补丁；补丁受 16 MiB
默认硬上限并以 `0600` 保存，SHA-256 写入交付结果。

随后控制器从相同 commit 建立新的 replay worktree，先执行 `git apply --check --binary`，再实际应用。
项目若配置 `verification_command`，则使用固定 argv 和超时在 replay 目录运行，不接受模型临时更改
复验命令。验证副本完全由控制器创建，完成后可以强制删除；Agent 原工作树只有在干净时才允许删除。

## Git、Shell 与 Docker 边界

Git 的 status、diff 和写操作全部由 Shell 执行，避免重新包装并追赶 Git 不断发展的参数、认证和配置
语义。这样所有 Git 命令共享同一个 `process` 权限、超时、取消和输出限制。Local 后端可执行本机允许的远端操作；Docker
当前默认断网，因此容器中的 fetch/pull/push 会明确失败，直到后续网络 Action 和审批边界实现。

曾实现的 `git_status`、`git_diff` 和 Docker 控制器特判已经整体删除。它们只节省一次只读 Shell 审批，
却增加了三个实现文件、条件注册、两套 Docker 执行位置和不同的 Git 参数能力。统一到 Shell 后，模型只需
学习一种 Git 入口，工具 Schema 也更小；只读 Git 需要审批是当前明确接受的取舍。

Docker worktree 的 `.git` 指针指向控制器的
Git 元数据，该元数据没有挂进容器。由此，显式 worktree 与 Docker 组合时，Shell 中需要 `.git`
元数据的 Git 操作目前不可用；默认直写 Docker 工作区挂载完整仓库，可以执行本地 Git 操作。

## 关键失败场景

1. **普通目录不是 Git 仓库**：默认直写仍可使用；只有模型实际运行 Git 命令时才由 Git 返回状态，也可
   先执行 `git init`。显式 worktree 模式则在创建后端前说明需要已有 commit。
2. **源工作树有修改**：默认直写保留并基于这些修改继续工作。显式 worktree 模式只读取 commit；若项目
   打开 `require_clean_source`，则在产生后端或模型副作用前拒绝脏起点。
3. **补丁无法重放或验证失败**：交付状态为 `failed_retained`，保留原 worktree、补丁及清单，CLI 返回
   非零；不会把模型的“完成”当成可交付成功。
4. **并行任务修改同一路径**：每个 task 使用不同 worktree 和 index，互不覆盖；本阶段不自动合并，
   因此合并冲突留给用户或后续协作阶段处理。
5. **清理路径或所有权不匹配**：拒绝删除；有未提交内容也拒绝自动清理。

## 验收

- 两个任务从同一 commit 并行创建 worktree，分别修改同一文件，源仓库保持干净且两个补丁不同。
- 补丁实际包含新增、删除、可执行位变化和二进制修改，并在干净 replay worktree 通过固定断言。
- 注入 replay 冲突后返回 `failed_retained`，原修改和补丁仍存在，临时验证副本被清理。
- 产品链 fake Provider 在隔离 worktree 写文件，源目录不出现该文件，结果包含复验通过的交付对象。
- 默认产品链在脏仓库直接写入目标文件，同时保留用户原有未跟踪文件。
- Shell 在未初始化目录完成 init、commit、branch，并通过本地裸仓库完成 fetch、pull、push。
- DeepSeek 官方 `deepseek-chat` 在真实 Rootless Docker 中只使用两个 Shell 调用完成 status/log 验证；
  中转站 `qwen-turbo` 与 `qwen3-coder-plus` 的空流或不完整流按协议错误停止，零工具副作用。
- 真实 Qwen 与 Rootless Docker 验收结果单独记录，不能由确定性测试替代。
