## 已有能力怎样增强

- 直接工作区：增加初始版本、用户差异归属、强制冲突前置条件和安全撤销；不回退到默认 worktree。
- 基础工具：分页读取、搜索覆盖范围和跳过原因；不以增加工具数量为指标。
- Context：先补截断前输出，再补完整请求预算和滚动检查点；摘要通过不等于语义无损。
- CLI：会话 ID 升级为真正连续对话；可诊断错误升级为能力协商及有界请求尝试。
- Docker：区分输出配额、可写层配额、bind 存储配额；修复 worktree/Git 边界时不得暴露全部宿主元数据。
- 评测：从当前阶段维护回归集，正式阶段冻结版本、预算和重复策略；分开模型自述、工具结果、Runtime 与独立判定。

## 重要失败场景与设计约束

1. 参数在批准后改变：Action 摘要/策略/工作区复核，不复用旧授权。
2. 磁盘满或输出超限：保留 partial/quota_exceeded，不发布完整引用；字节统计区分观察和保存。
3. 副作用已经发生但控制器崩溃：恢复为 unknown/needs_reconciliation，不无条件重放写入、commit 或 push。
4. 脏目录被用户再次编辑：修改/撤销核对版本，不能用 reset/clean 丢弃劳动。
5. 仓库配置提供恶意 URL/Hook：不可信项目只能收紧权限，秘密和信任上限由用户控制。
6. 隐私日志与恢复冲突：正文进入独立限权存储，默认 Trace 只含元数据。

这些是后续必须验证的故障契约，本轮没有运行故障注入，也没有宣称实现其防护。
