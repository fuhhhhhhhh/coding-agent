# P1 设计：统一产品主链

## 范围

P1 把已经存在的 Runtime、工具、权限、调度、Context、Trace 和 Local/Docker 后端接入同一个正式入口：

```text
codepilot / codepilot run
  -> 分层 ProductConfig
  -> CodePilotApplication
  -> ExecutionBackend
  -> ContextManager
  -> ScheduledExecutor
  -> PermissionedExecutor
  -> Provider + Runner
  -> RuntimeEvent -> EventRenderer
```

本阶段没有实现 worktree、会话恢复、PTY、后台任务、Skills、Hooks、MCP、完整 Provider 能力协商或复杂重试。`session_id/task_id/run_id` 已成为稳定关联键，但 P5 之前仍不能通过 `resume` 恢复进程。

## 目录与职责

```text
src/codepilot/app/
  models.py       # 运行身份、资源归属和产品结果
  service.py      # composition root 与统一生命周期
src/codepilot/ui/
  cli.py          # 交互外壳、单次 run、配置覆盖和退出码
  renderer.py     # 只消费 RuntimeEvent 与 ProductRunResult
src/codepilot/providers/
  openai_compatible.py  # 最小 Chat Completions 兼容边界
src/codepilot/config.py # 用户/项目/显式文件/CLI 四层配置
```

UI 不直接调用 SDK 或工具。`EventRecorder` 在事件已经进入规范内存轨迹并完成可选脱敏落盘后，把事件副本交给 renderer。人类模式可以展示流式正文；JSONL 进度沿用 Trace 的正文省略策略，最后单独输出产品结果。

## 配置和秘密边界

配置优先级从低到高为：

1. 代码默认值。
2. `$XDG_CONFIG_HOME/codepilot/config.yaml` 或 `~/.config/codepilot/config.yaml`，兼容原 TOML。
3. 工作区 `.codepilot/config.yaml`，兼容 `.codepilot.yaml` 和原 `.codepilot.toml`。
4. `--config` 指向的显式文件。
5. 用户明确提供的 CLI 选项。

YAML/TOML 嵌套对象递归合并，因此高优先级文件只需覆盖一个字段。同一层若存在多个候选配置会
拒绝启动，避免产生隐式选择。YAML 使用 `safe_load`、限制为 256 KiB 且要求对象顶层；所有字段再由
严格 Pydantic 契约校验，未知字段拒绝。普通配置只保存 `api_key_env` 和 `api_key_file` 来源，真实值
可以来自临时环境变量，或权限受限的用户级 `credentials.yaml`；环境变量存在时优先且不读取文件。
凭据文件拒绝符号链接、非当前用户所有、组/其他用户可访问、超过 16 KiB、损坏 YAML、未知字段和
空密钥。密钥只在应用对象内存中交给 SDK，不进入 Runtime 契约、Trace、后端环境或产品结果。

## 交互外壳

无子命令的 `codepilot` 是面向人的默认入口；`codepilot run "任务"` 保留为自动化入口。交互外壳
只负责读取任务、生成 ID、调用同一个 `_run` 并展示结果，没有复制 Runtime 循环。一次进程内的任务
共享 session ID，每条输入生成新的 task/run ID 和独立 Trace。空输入不执行，`/help` 只展示本地
帮助，`/exit`、`/quit` 或 EOF 正常退出；单条任务受控失败或意外启动异常不会关闭提示符。

当前 session ID 只是关联键，交互任务之间尚不共享模型消息；持久对话、恢复和历史分支仍属于 P5。
这个边界会在启动文案和学习记录中显式说明，不能把“同一交互进程”描述为“已经支持持久会话”。

`fake` 和 `openai-compatible` 共用内部 Provider/StreamingProvider 边界。兼容适配器关闭 SDK 自动重试并使用显式请求额度。P1 只承诺 Chat Completions 基本流、工具调用和 usage；模型能力表、限流分类、费用硬上限及第二协议属于 P6。

## 状态所有权与清理

一次运行有三层 ID：

- `session_id`：未来持久会话的关联键。
- `task_id`：用户任务及后续 worktree 的归属键。
- `run_id`：一次 Runner 尝试和 Trace 的唯一键。

状态目录布局为：

```text
state/session_id/task_id/run_id/
  traces/    # 保留的脱敏 Runtime Trace 和摘要
  backend/   # 保留的后端生命周期审计
  context/   # 当前运行临时 Artifact，退出时清理正文
```

`AsyncExitStack` 是 composition root 的唯一清理出口。资源一经构造就立即登记：退出时先关闭 SDK 客户端，再关闭后端，最后删除当前 Context store 登记的临时文件。Provider 装配失败、后端部分启动失败、Runtime 正常结束和异常结束都经过这个出口。

外部取消由 Runner 先记录唯一 `cancelled` 终态，再由产品层调用 `backend.cancel()` 封闭入口并停止活动进程或容器，随后进入幂等 `close()`。取消仍向调用方传播，CLI 将 Ctrl-C 映射为退出码 130。

## 权限和包装顺序

执行链采用：

```text
backend <- context <- scheduler <- permission <- runner
```

Context 收到普通工具结果后决定是否落盘；Runner 执行工具时先经过 permission 和 scheduler，因此 `read_context_artifact` 也经过同一个入口。权限层新增只读 `specs` 转发，使 Provider 能看到最终工具目录。`find_backend` 仍可沿各层的 `registry` 找到真实 Local 或 Docker 后端。

P1 保留现有三种权限预设。CLI 默认 `ask-edits`，涉及写入或 Shell 时要求终端明确批准；自动化 fake 和真实 Qwen 验收使用 `read-only`。规范化 Action、网络/环境/秘密权限属于 P3。

## OpenAI-compatible 兼容故障

云锦淘令牌的 `/v1/models` 查询返回多个 Qwen 型号。`qwen-turbo` 的生成接口在本次环境中返回空流/无有效 choices，不能作为成功证据。随后选择 `qwen3.5-flash` 做受限验收。

第一次 `qwen3.5-flash` 工具流暴露出一个协议差异：网关在合法工具参数之后发送了只有 `index` 的空占位 tool-call delta。严格 `StreamChunk` 正确拒绝无信息片段，但适配器把供应商占位项错误地提交给了内部契约。修正后，适配器在边界丢弃完全不推进组装的占位项；省略 index 的单工具分片归入第零组。不同 ID、非法 JSON、错误 finish reason 和数据出现在 finish 之后仍会失败。

真实快速排序任务又暴露了输出截断的可诊断性问题：模型先完成 `glob`，第二轮开始生成
`write_file`，但 512 Token 上限在完整 JSON 结束前触发 `finish_reason=length`。组装器原本正确保持
零写入，却把它归为笼统 `contract_error`。现在适配器抛出专用 `OutputLimitError`，Runtime 终态为
`output_limit`，终端说明不完整调用未执行；产品配置提高到 2048 Token。这个分类不能放宽原子组装
边界，截断参数仍不得送入工具。

MockTransport 回归测试固定复现该布局，避免依赖真实服务的随机输出验证正确性。

## 关键故障场景

- **非法配置**：未知字段、不可能的 Provider/后端组合、状态目录位于工作区内、空任务均在副作用前拒绝。
- **Provider 初始化失败**：已经构造的 ArtifactStore 和后端进入统一清理出口；后端即使未启动也记录一次 closed。
- **后端部分启动失败**：模拟握手前已经进入 started，异常后仍调用 close，不继续请求模型。
- **外部取消**：Runner 只写一次 cancelled 终态，后端依次记录 started/cancelled/closed。
- **兼容流占位项**：空占位不进入内部分片；真正冲突或不完整流继续明确失败。
- **输出额度截断**：产生 `output_limit`，已有完整工具结果保留，当前半截调用保持零执行。
- **密钥缺失**：显示已配置的来源名以便诊断，不从普通产品配置读取内联秘密，也不创建状态目录。
- **凭据文件不安全**：归属、权限、符号链接、大小和 Schema 任一不满足都在创建运行资源前拒绝。
- **配置歧义或损坏**：同层多个文件、损坏 YAML、非对象顶层和超大文件均在装配前拒绝。
- **交互任务失败**：只终止当前任务并保留提示符；异常正文不直接输出，避免携带请求或凭据。

## 验收证据

- fake + Local：两轮模型、一次 glob、权限允许、Trace 和后端审计均通过，结束后后端关闭、Context 临时正文清理。
- fake + Rootless Docker：通过相同 `codepilot run` 命令完成一次 glob；真实容器启动、工具执行和关闭成功。
- `qwen3.5-flash` + Local：两轮流式请求、一次 glob、最终中文回答成功；输入 3,826 + 3,955 Token，输出 110 + 26 Token；总运行约 10.6 秒。
- `qwen3.5-flash` + Rootless Docker：在一次性仓库中先经历 edit 冲突，再读取文件、精确编辑、等待 Shell 人工审批、运行 unittest 并完成最终回答。5 次请求、4 次工具调用；输入 9,122、输出 371 Token。控制器随后独立复验测试和文件内容。
- 交互 CLI：自动发现 YAML、共享 session/独立 task 和 run、连续两次 fake 任务、退出、EOF 等路径由确定性测试覆盖；`uv run codepilot` 实际提示符冒烟通过。
- 固定凭据文件：清除 API Key 环境变量后，安装版 `codepilot` 从 `0600` 用户 YAML 认证，真实 `qwen3.5-flash` 完成一次无工具回答，Rootless Docker 正常关闭且无受管容器残留。
- 输出截断恢复：原任务证明确实在 `write_file` 参数中达到 512 Token；提高上限并细分终态后，真实重试创建快速排序文件、执行 Shell 测试并通过独立函数检查。
- DeepSeek 本轮未重试；其服务故障状态不再阻塞 P1。

写入验收成功前还有三个独立失败 run：一个首轮连接失败，两个在首个只读工具后的第二轮连接失败。三者均以 `provider_error/APIConnectionError` 停止，工具副作用没有越过已完成步骤，容器正常回收。详细结果保存于 `docs/evidence/P1-checks.txt`、`docs/evidence/P1-live-checks.json` 与 `docs/evidence/P1-real-write-shell.json`。
