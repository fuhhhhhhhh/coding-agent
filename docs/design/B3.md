# B3：长任务、恢复与 Provider 可靠性

状态：B3 核心链与收尾门槛通过 Linux Local、Rootless Docker、官方 DeepSeek Flash 双协议和干净 Python 3.11 安装的受限验收；不是整个 Coding Agent 产品就绪。日期 2026-10-19 UTC。

## 本轮交付：可诊断、可审查的持久恢复

B3 收尾覆盖原计划的备份迁移、真实崩溃矩阵、版本化控制器事实、上下文审查/撤回与能力费用边界。产品入口和失败语义如下：

| 用户入口 | 实际行为 | 关键保护 |
| --- | --- | --- |
| `sessions backup ID` | SQLite 一致性备份，0600，保存在本会话 backups | 与运行共用写锁；只备份数据库，不伪装成工作区/输出全量备份 |
| `sessions migrate ID` | 从数据库 v1 升到 v2，事件仍为 v1 | 先备份、核对事实，再以事务创建快照表和改版本；失败回滚；未来版本拒绝 |
| `sessions restore ID backup-….db` | 先备份当前库，再原子恢复所选数据库 | 不回滚代码；要求当前无未知/活跃 run；保留较大累计预算与未知预留，恢复后强制协调 |
| `sessions diagnose ID` | 列出 calls/resources/provider_pending 和恢复阻碍 | automatic_replay 始终 false；活跃进程不能仅靠用户确认跳过 |
| `sessions facts ID` | 控制器执行记录、目标修订号、修改版本及是否仍适用 | run/call/sequence 来源；工作区版本变化使旧执行 current=false；exit_code=0 不是需求验收 |
| `context ID [show|summary|reset]` / `/context` | 查看估算与用量；显式查看摘要；归档撤回 | reset 不删消息、不回滚文件；暂停自动压缩，显式 compact 才重新启用 |

数据库 v2 的 `snapshots` 保存覆盖序号、事件前缀与快照内容的联合校验和及状态视图。重开先核验来源，再载入快照和重放后缀；快照不替代事件。偏移越界、前缀/内容不匹配、未知事件版本和序号缺口都停止。旧数据库明确提示 `sessions migrate`，不在用户普通任务中静默升级。`inspect` 对 v1 仍可只读查看。

控制器在工具意图前保存归属，结果时记录工具成功/错误、Shell 退出码和工作区 stamp，保留最近 100 条可查询记录，Prompt 仅带最近四条和六条路径变更。原始完整事实仍在事件历史。仓库规则放入用户任务数据；只有内置显式 trusted 规则使用 system。模型候选摘要要求严格 JSON 的 summary/source_indices，校验字段、非空及来源编号范围；它的语义仍可能出错，不会写成控制器独立验收。

事实视图在上下文压缩完成后重新构造，放在最近用户请求之前，不进入规范历史或改变检查点来源哈希。最初真实测试放在末尾触发两协议 BadRequestError，修正后两者通过；增加了保护最新用户消息顺序和工具调用/结果原子组的回归。这个兼容性失败保留在 evidence，不用最终成功覆盖。

恢复协调通过真实 os._exit 覆盖三处：模型实际调用前、Shell 写入后仍存活、Shell 完成而结果未入库。控制器重开都阻断；运行中的精确归属进程阻止协调，测试清理后才可继续；未知结果补成错误而非成功，新 run 不再追加副作用。Linux 僵尸已无法执行副作用，不能永久算活跃资源。恢复不承诺跨外部系统 exactly-once。

能力表按精确官方 endpoint/model/protocol 匹配。未知网关即使模型同名也不套用官方规格/价格；超已知窗口在创建任务目录和请求前拒绝。已知价格以发送时费率保存到每次预留，按 usage 做十进制估算；换模型不重算旧请求。使用带日期的峰值、缓存未命中估算，不是账单。pending、旧会话和未定价请求明确未知；备份恢复不能重置已消耗额度。具体组合矩阵见 `../evidence/B3-provider-matrix.md`。

本轮验证：离线 281 passed / 7 skipped；Rootless Docker 7 passed；Ruff、格式、mypy、wheel 及干净 Python 3.11 安装验收。真实官方 DeepSeek 两协议各在两个模块的 Unicode 标签合并缺陷上先失败再修复，公开/隐藏测试、保护文件、严格摘要、新进程续问、撤回与私有备份通过。共 20 次尝试（初始失败 2 + 修正后 18），成功链 usage 64,179 输入 / 9,704 输出；初始失败 usage 未知，不能按零计费。四层记录见 B3-finish-live*.json；命令、失败与未运行项见 B3-finish-checks.txt。

参考：[Python 3.11 SQLite backup](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Connection.backup)、[DeepSeek 模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)。未复制外部 Agent 代码；沿用标准库 SQLite 和锁定 SDK。

## 解决的问题与产品入口

以前预算按主回合统计，摘要与重试容易绕开共享次数；检查点虽然落盘，重开后仍重复压缩全量历史；只有 Chat Completions 适配。现在沿现有 Application → Context → Provider → Runner 链补齐这些行为，不引入第二套 Runtime 或会话数据库。

默认模型与 Chat Completions 不变。`codepilot --protocol responses` 可选择第二协议；交互 `/compact` 或 Shell `codepilot compact SESSION_ID` 主动压缩历史。命令经过原有工作区/会话检查、期限、后端清理和 Trace，只执行摘要请求，不执行主请求或工具。历史不足时只做检查，不能保证每次都会产生摘要。`sessions show SESSION_ID` 可查 provider_budget，私有正文不作为默认 Trace 输出。

## 内部契约与状态所有权

| 所有者 | 契约与边界 |
| --- | --- |
| RequestBudget / BudgetLedger | 每次尝试生成 attempt_id；预留消息、Schema、包装输入估算及实际 max_tokens 输出；usage 按身份结算，响应乱序不串账 |
| SessionStore | 网络前事务写入 request_attempts 与 provider_budget；记录实际 input/output、pending 和旧会话 legacy_requests_without_usage；resume/reconcile 不释放未知成本 |
| RetryPolicy / Provider | 默认三次尝试、1 秒指数退避、最长等待 30 秒；SDK 重试设为零。重试等待受 Runtime 总时限与取消控制 |
| ContextManager | 规范历史不变，只产生 Provider 视图；保留初始用户约束及最近完整回合，摘要是 assistant 历史数据，不能提升成 system 授权 |
| CheckpointStore v2 | covered_messages、规范历史 source_digest、summary_digest、usage、前后估算与模型提出的 WorkingState；0600 原子替换，私有目录拒绝符号链接 |
| ResponsesProvider | 只负责 Responses 语义事件到内部 StreamChunk 的转换；与 Chat Completions 共享预算、重试、工具校验和 Runner |

输入估算是近似值，不是 tokenizer 硬证明或服务端账单。默认会话输入/输出总额度为 100M / 10M；Provider 单任务可设置 total_input_tokens / total_output_tokens。旧会话无法补出历史 usage，必须保留“未计量”提示。未知 usage 保留请求占用和相应 Token 预留；未知费用不能按零宣称账户硬封顶。

## 正常数据流

1. App 检查会话身份、工作区及历史配对，装配真正无工具的摘要 Provider；它与主 Provider 共用客户端和 RequestBudget。
2. Context 在阈值检查前载入检查点，验证版本、摘要校验和、规范消息前缀哈希与完整回合边界。匹配时复用摘要及未覆盖历史；漂移时从规范历史重算，损坏时停止且保留原文件。
3. 再次压缩只发送“上一摘要 + 新增旧回合”；新检查点覆盖完整规范前缀，不以摘要替代 SQLite 原文。100 回合测试每 20 回合模拟新进程的 Context 实例，核对滚动输入不重复全部原文。
4. Provider 组装消息和工具 Schema，预检完整估算与输出预留，再以同一 attempt_id 更新内存和 SQLite。只有持久预留成功才发送 HTTP。
5. 主请求和摘要收到 usage 后分别按 ID 结算。正式 provider 的 model_requested 不再重复扣次数；fake Provider 保持原有受控计数。
6. 两协议都必须完整终态并通过工具参数组装/校验才允许执行工具。Responses 保留函数 call_id，检查序号、逐项完成参数、最终输出集和 response.completed；恢复发送本地规范历史，store=False，不依赖服务器 previous_response_id。
7. 工具仍走审批、调度、Docker/Local、输出捕获和 Trace。运行退出由原资源栈关闭客户端、工具后端和会话锁。

## 重试与故障语义

- 429 是明确拒绝，允许有限重试；数值/HTTP 日期 Retry-After 在有效等待范围内才使用。格式非法、负数、非有限值或超过上限时停止，不提前重试。
- APIConnectionError 仅底层明确 ConnectError / ConnectTimeout 才重试；ReadError、读写超时、500、认证/余额错误不重放。仅创建流的调用允许重试，消费中的半截文本/工具流失败直接停止。
- 每次尝试都有 provider_attempt / provider_retry 与 attempt_id；默认不输出 SDK 错误正文、请求正文或密钥。已明确拒绝的请求按零 usage 结算，未知是否接受保留 pending。
- 预算不足时发送次数为零或停在已发送边界；已收到的超报仍先记账再停，不能丢掉服务端实际事实。真实控制器 os._exit 注入确认 pending 与 running 保留，重开须协调。
- 检查点摘要超目标、摘要失败或写入失败均不发送明知超预算的主请求；未知版本、损坏 JSON、校验和不匹配明确停止。v1 可读但没有覆盖范围，不能直接复用为 v2，下一次正常压缩才写新格式。
- 摘要中的“测试通过”只是模型建议，不是控制器验收；WorkingState 的标题提取尚未成为带源码版本的可信事实层。

## 2026-10-19 下一组 B3：跨控制器限容任务恢复

B3 已有受限验收，本轮是新执行模式的恢复闭合，不重复宣布“从零开始 B3”。用户明确指定推进 B3，B2 网络/秘密仍为发布缺口，但不是断网恢复的前置条件。阶段状态以后区分已实现能力、当前开发主题和发布阻断，不能把回补顺序描述成 B3 从未开始。

统一入口新增 recover SESSION RUN [--apply]，默认只读预览；显式应用仅核对归属、保存产物、清理自有资源。每个 bounded run 在 Docker create 前持久化随机名称/后端绑定、镜像 ID、配额、根目录身份；创建、导入、检查点、最终导出、关闭逐阶段保存。恢复要求会话排他锁、源身份、私有清单、Rootless daemon、容器标签/名称/镜像/内核约束均匹配。旧 run 没有绑定则拒绝猜测。

归档由现有固定协议导出，SHA-256 与容量核验后才能覆盖私有镜像、删除容器。活容器先停写再导出；已停止/消失的容器只接受完整已知检查点并明确 data_loss_possible，不能假装最新产物已保存。工具不重放、源文件不修改、Provider 不请求、未知调用与费用预留不清零。恢复后保留 needs_reconciliation，再由显式协调和原 delivery 完成后续。应用中断可以重新读取阶段并继续资源恢复，不继续原 Shell 或源目录 applying/undoing 的未知写入。

正常路径、导出/删除/存储失败、daemon 不可达、归属漂移、检查点损坏、会话竞争、真实控制器被杀后的恢复均须验收；未关闭的孤儿资源和未交付产物不能被 prune/delete 静默删掉。验收命令：pytest 严格资源警告、ruff check/format、mypy、wheel 字节检查；之后 Rootless Docker 实际崩溃/恢复/源版本冲突，再做有限官方 DeepSeek 续问。最终保留模型/工具/Runtime/独立判据四层结论。

### 状态、提交点及失败边界

`bounded-container.json` 保存 version、随机 backend_id/name、container_id（创建返回前为空）、镜像 ID、Rootless owner、私有目录设备/inode、main_pid、配额和阶段 creating/created/seeding/active/exported/closed。绑定在 create 前写入，回收对象由该随机身份和 daemon inspect 独立确认，不从模型自述取身份。当前版本之前没有绑定的 run 明确拒绝，不能补造所有权。

检查点保存在 `bounded-checkpoints/<sha256>.tar`，哈希指针提交后才回收旧归档；`bounded-latest.tar` 仅兼容查看。活容器最终导出使用原固定归档协议并先暂停写进程。导出/保存失败不删容器，删除失败仍保留 exported 和可重试清单。已停止或消失的已知容器只使用指针引用的完整归档，报告 `data_loss_possible=true`；创建尚未返回且查无对象不能证明未接受，必须保留 creating。恢复只读容器状态或保存/清理，不重放旧工具，不自动继续源目录 applying/undoing。

Docker 控制操作、启动握手和归档操作有 60 秒等待上限；客户端超时不证明 daemon 未接受，也不自动重发。资源采样 3 秒超时只跳过采样。实际环境曾出现 build/create 长时间等待：首轮测试在副作用屏障前退出，保存失败记录；稍后用 creating 绑定找到精确 Created 容器并安全回收。停止本轮自有构建客户端后再次真实崩溃链通过，未修改或重启公共 Docker。

`recover` 持原会话锁，默认只读，`--apply` 保存产物并结束精确容器资源。会话仍 needs_reconciliation，旧调用、未知费用与预算不清零。之后沿原 reconcile/delivery/resume 使用，源版本漂移继续拒绝交付；重复恢复不逆转已应用状态。sessions diagnose 展示 bounded_workspaces，协调拒绝活盘/未知源交付；delete/prune 保留未交付产物。

新增代码只运行在宿主控制器，容器内固定 archive/worker 工具协议未改。真实组合验收使用已有 codepilot-sandbox:0.1.0，启动时核对工具 Schema；本轮新镜像全量构建因上述等待取消，不声称新镜像全部源码字节已核验。wheel 包含全部新控制器源码。网络仍 none，秘密注入、Windows/macOS、任意源写入 exactly-once 和掉电耐久性不在本轮通过范围。

本轮主要修改：`app/operations.py::recover` 持锁装配；`app/service.py` 给资源关联 run；`workspace/recovery.py` 新增绑定核验和产物恢复；`workspace/docker.py` 增加持久阶段、提交顺序与控制面期限；`sessions/store.py` 增加诊断和协调/删除保护；`ui/cli.py` 接命令与 slash 入口；两个 B3 bounded 测试文件覆盖模拟故障和真实控制器退出。目录沿原 app/workspace/sessions/ui 分工，没有第二套 Runtime。最终相关六项 Rootless 再验通过，详见 final-bounded evidence；本轮真实续问使用 Chat Completions，不追加宣称新的 Responses 联合验收。
