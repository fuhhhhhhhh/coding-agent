# M05：策略权限与 CLI 审批

## 范围

M05 在工具注册表前增加独立的权限包装层，提供 `allow`、`deny`、`ask` 三种决策，
按工具名称、影响类型和路径前缀匹配规则，支持脚本化审批和 CLI 标准输入审批，并留下可序列化审计记录。

权限层不执行文件路径安全检查、不提供容器隔离，也不把危险命令黑名单当作安全保证；最终工具仍由 M03/M04
的 Workspace 和 ToolRegistry 校验。容器模式在后端不存在时显式拒绝。

## 数据流

```text
ToolCall + ToolSpec
        ↓
PermissionEngine.decide
        ├── deny  → PermissionAudit + ToolResult(permission_denied)
        ├── ask   → ApprovalProvider
        │             ├── false → Audit(cancelled) + ToolResult(permission_cancelled)
        │             └── true  → Audit(approved) → ToolRegistry.execute
        └── allow → Audit(allowed) → ToolRegistry.execute
```

`ApprovalRequest` 深拷贝完整 `ToolCall` 和 `ToolSpec`，审批答案绑定具体参数。下一次参数变化会生成新的
请求 ID，不能复用先前审批。`PermissionedExecutor` 是现有 `ToolExecutor` 形状，因此 Runner 不需要知道权限实现。

## 规则与预设

- `read_only_policy`：只允许 `effect=read`，写入和进程拒绝。
- `ask_edits_policy`：读取允许，写入和进程每次审批。
- `controlled_edit_policy`：读取和写入允许，Shell 等进程调用每次审批。

规则采用拒绝优先：所有命中规则中只要有 deny 就拒绝；没有命中时使用策略默认值。路径规则使用模型传入的
相对路径做前缀匹配，真正的越界和符号链接检查仍由 Workspace 执行，权限规则不替代执行边界。

`ConsoleApproval` 使用 `asyncio.to_thread(input, ...)`，标准输入中只有明确 `y/yes` 才批准；EOF、其他输入
和用户取消都视为不批准。测试和离线演示使用 `ScriptedApproval`，不读取真实终端。

## 审计与边界

每次判定都会生成 `PermissionAudit`，记录序号、请求 ID、调用 ID、工具名、决策、结果和原因，不保存 API 密钥。
拒绝和取消发生在 ToolRegistry 之前，因此不应产生工具副作用。权限允许不等于工具执行成功；参数错误、路径错误、
工具异常仍由 ToolRegistry 和 Runner 记录。

`container_mode=true` 直接返回 `container_mode_not_implemented`。这保证配置不会把“计划中的容器策略”误报为实际隔离。

## 验收

```bash
uv run --locked ruff format --check .
uv run --locked ruff check .
uv run --locked mypy src tests
uv run --locked pytest -q
uv run --locked python -m codepilot.m05_demo
git diff --check
```

当前 Linux/Python 3.14.7 环境中 98 项测试通过。覆盖只读拒绝、审批取消、审批通过、完整参数绑定、
拒绝优先和未实现容器模式。Windows/macOS、真实 CLI 交互和真实隔离后端未验证。
